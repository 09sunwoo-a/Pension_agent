# 09 코어 비즈니스 로직 — 정제 작업 지침

> 이 디렉토리의 문서를 수정하는 모든 작업(사람·Claude)이 따르는 규칙.
> 목적: 원천 코퍼스(01~08)를 분석해 퇴직연금 **사후관리** 업무의 핵심 Business Logic을 발견하고,
> 에이전트 모델 로직 구축의 기초가 되는 코어 문서(00~05, 10)를 정제·유지한다.

## 0. 최상위 원칙 — Extraction보다 Model Refinement가 우선

- 코어 문서는 "발견된 정보의 수집함"이 아니라 **업무의 모델**이다.
- 새로운 자료에서 좋은 정보가 발견되었다는 이유만으로 Core 문서에 추가하지 않는다.
- 항상 현재 모델과 비교하여 ①무엇이 새롭고 ②무엇이 이미 설명되며 ③무엇이 단순 사례인지 판단한다.
- 문서의 가치는 길이가 아니라 **설명력 대비 밀도**다. 추가해서 모델의 설명력이 늘지 않으면 추가하지 않는다.

## 1. 판단 플로우 — 원천 문서를 읽을 때의 기본 사고 순서

원천 문서를 읽으면서 바로 Core MD를 수정하지 않는다. 정보 단위마다 아래 순서로 판단한다.

```
새로운 정보 발견
      │
      ▼
0. 배제 필터에 걸리는가? (§3) ── YES → 코어에 넣지 않음 (필요 시 별도 트랙 메모)
      │ NO
      ▼
1. 기존 모델에 이미 설명되어 있는가?
      │
      ├─ YES → 기존 항목의 근거 강화 / 구체화 여부만 검토 (§2-1)
      │
      └─ NO
           ▼
2. 전체 Business Process 구조를 바꾸는가?
      │
      ├─ YES → 00 수정 검토 (§2-2)
      │
      └─ NO
           ▼
3. 특정 단계의 새로운 방법론 또는 하위 구조인가?
      │
      ├─ YES → 01~05 중 해당 문서 수정 검토 (§2-3)
      │
      └─ NO
           ▼
4. 재사용 가능한 상태·조건·제약·Action인가?
      │
      ├─ YES → 10 수정 검토 (§2-4)
      │
      └─ NO
           ▼
5. 단순 사례·성공담·화법·현장 팁·배경 설명인가?
      │
      ├─ 중요한 근거 → 기존 항목 Evidence(출처 태그)로 사용 (§2-5)
      └─ 그렇지 않음 → Core 문서에 넣지 않음
```

## 2. 각 갈래의 구체 기준

### 2-1. "이미 설명되어 있는가" — 기본 가정은 YES

- 대부분의 발견은 기존 룰·원칙을 **다른 어휘로 말한 것**이다. 표현이 달라도 같은 로직이면 신규가 아니다.
- YES일 때 할 수 있는 일은 4가지뿐: ⓐ 출처 태그 추가(출처 다변화 = 근거 강화) ⓑ `검토중` → `확정` 승격 ⓒ 조건식·수치의 구체화(비어 있던 임계값·분기를 원문 수치로 채움) ⓓ 아무것도 하지 않음.
- 태그 추가도 무한정 하지 않는다 — 항목당 3~4개면 충분. 이미 "현장 다수"로 표기된 항목엔 더 달지 않는다.

### 2-2. 00 수정 — 전체 구조 변경 (가장 드물어야 정상)

- 5단계 플로우 자체, 관통 원칙(G1~G7), 공유 자산 구조(단계↔카탈로그 관계)를 바꾸는 발견만 해당.
- 파급이 크므로 즉시 반영하지 않고 **변경 제안으로 사용자에게 보고**한 뒤 반영한다.

### 2-3. 01~05 수정 — 단계 방법론

- 해당 단계의 세부 단계(x-y) 안에 새 방법론·하위 구조가 생기는 경우.
- 새 세부 단계(x-y) 신설은 신중히 — 기존 세부 단계의 항목으로 들어갈 수 있는지 먼저 시도한다.
- **조건식·액션을 01~05에 직접 정의하지 않는다.** 10 카탈로그의 ID(R-/A-) 참조만 한다. (임계값 드리프트 방지)

### 2-4. 10 수정 — 룰 카탈로그

- 재사용 가능한 상태·조건·제약·Action → R-(해당 계열) / A- 신설 또는 기존 룰의 필드 보강.
- 신설 기준: 모집단에 조건식으로 배치 실행 가능하거나, 복수 단계에서 재사용되는 것.
- 확신이 낮으면 본 테이블이 아니라 **「검토 대기 목록」에 먼저** 넣는다. 원문 재검증 후 승격.
- 임계값은 원문 수치를 그대로 옮기고 출처·기준시점을 단다. 수치 재조정은 팀 몫이다.

### 2-5. 사례·성공담·화법·팁·배경

- 기본은 배제. 코어에 넣지 않는다 — 화법 원문·사례의 저장소는 06/08 등 다른 폴더다.
- 예외: 기존 항목의 주장을 실증하는 중요한 근거일 때만, 해당 항목의 **출처 태그로만** 흡수한다 (본문 서술 추가 금지).
- 화법에서 코어로 올라오는 것은 대사가 아니라 **구조**다 (분기 질문, 시퀀스, 금지 규칙).

## 3. 항상 배제 (판단 플로우 진입 전 필터)

| 배제 대상 | 처리 |
|---|---|
| 은행 이익 전술 (락인 상품 유도, KPI 득점 시기 전술, 계열사 이전 유도, 등급 락인, 경품 유인) | 코어 제외. 00 「별도 트랙」 언급 유지, 필요 시 추후 리텐션 전술 트랙에서 정리 |
| 신규 유치·기업형 DB/DC 전용 로직 | 범위 밖. 단, 사후관리 관점으로 재해석되는 부분(예: 퇴직금 수령 시점 대응)만 판단 플로우로 |
| 특정 시점의 상품명·금리·수익률 수치 | 코어에 넣지 않음 (주기 갱신 재료, G7). "월 갱신 풀이 존재하고 이를 참조한다"는 **구조**만 코어 |
| 단순 조작법·화면번호·절차 스크린샷 | 코어 제외. 단, 실행 함정(순서·선행조건·기한)은 A- 액션의 「실행 경로·함정」 필드 후보 |

## 4. 편집 규약

- **출처 태그**: 00 문서 하단의 태그 체계를 사용한다. 새 원천 문서군이면 태그를 00에 등록한 뒤 사용.
- **상태 라벨**: `확정`(원문 검증 완료) / `검토중`. 승격·강등 시 근거를 함께 갱신한다.
- **신뢰 라벨**: 본부공식 / 현장팁 / 대외공개(고객 제시 가능) 구분 유지 (G2).
- **빈칸 섹션**(`- [ ]`)은 모델의 알려진 공백 목록이다. 채워지면 항목을 지우고, 새 공백을 발견하면 추가한다.
- **버전**: 실질 변경 시 문서 헤더의 vX.Y와 날짜를 올린다. 변경 이력은 git 커밋이 담당 — 커밋 메시지에 "무엇을, 왜, 어느 원천에서"를 남긴다.
- **문체**: 선언문·표 중심, 한 항목 = 한 줄. 완성 대사 예시는 최소한으로.
- 06(주제별 추출지식)과 겹치는 항목은 상호참조(§표기)를 단다.
