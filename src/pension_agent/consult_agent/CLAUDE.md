# consult_agent 기준서

`consult_agent` — 영업점 직원과 대화하는 에이전트의 요건.

**이 문서는 기준이다. 구현 설명서가 아니다.** 코드가 이 문서와 다르게 동작하면 코드가
틀린 것이고, 문서를 코드에 맞춰 내리지 않는다. 알려진 불일치는 §12, 아직 하기로 정하지
않은 것은 §13 에 모은다 — 본문에는 "지금 코드는 ~한다"를 쓰지 않는다.

함께 보는 문서: 저장소 전체 원칙은 루트 `CLAUDE.md`, 사용법·현재 코드 구조는 `README.md`,
지식 데이터가 갖춰야 할 구조·관계는 `../knowledge/CLAUDE.md`.

## 1. 무엇을 하는 에이전트인가

직원이 고객을 상담하기 전과 상담하는 중에 옆에 두고 쓰는 도구다. 자연어로 물으면 **행원들이
정리해둔 행내 지식베이스**와 **지금 열려 있는 고객의 브리핑 재료**를 근거로 답하고, 필요하면
다음 행동(해당 업무 화면 열기·브리핑 수정)까지 잇는다.

### 하는 일

| 기능 | 무엇 | 요건 |
|---|---|---|
| **지식 질의응답** | 제도·상품의 값, 업무 절차, 단말 화면번호, 고객이 앱·웹에서 직접 하는 비대면 경로, 고객군 정의, 관리 판단 기준, 현장 관찰을 묻는 질문에 답한다. 대화형의 **주 기능**이다 | §3 재료 · §5 적절성 |
| **화법 코칭** | 상담 상황을 말하면 고객에게 할 말과 왜 그렇게 접근하는지를 짚어준다 | §3 · §5 |
| **반론 대응** | 고객 대사를 그대로 던지면 그 말에 어떻게 답할지 짚어준다. 화법 코칭과 같은 재료·같은 형태다 | §3 · §5 |
| **고객 브리핑 질의** | 열려 있는 고객의 현황·제안 근거를 묻는 질문에 답한다. 값은 전략제안이 계산한 것을 그대로 쓴다 | §3 |
| **금지·주의 안내** | 그 고객 상태에서 하면 안 되는 것을 지식베이스 근거로 띄운다(07/01 ① 요소 6 위임분) | §8 |
| **브리핑 수정 요청** | 화면의 AI 산문(제안 문장·근거 해설·카드 문구)을 대화로 고친다. 시스템이 계산한 값·상품·판정은 대화로 고칠 수 없다고 거절한다 | §3 |
| **화면 연계** | 답변이 가리키는 단말 화면(절차의 화면번호 · LMS 발송 화면 등)으로 바로 갈 수 있게 제안하고, 직원이 승낙하면 파라미터를 채운 딥링크를 준다 | §10 |
| **상담이력 기록·조회** | 모든 턴을 고객·세션 단위로 남기고, "지난번에 무슨 얘기 했지"에 그 기록으로 답한다. 쓰기는 대화형만, 전략제안은 읽기만 한다(단방향) | §2 · §3 |
| **능력 안내** | 무엇을 도울 수 있는지 스스로 답한다 | §3 |

여러 기능이 한 답변에 섞이는 것이 정상이다 — "이 고객 수수료 불만인데 우리 IRP 수수료가
얼마고 뭐라고 말하지"는 값·고객 재료·화법이 한 답에 들어간다.

### 누가 읽나 — 직원용이다

답을 읽는 사람은 영업점 직원이고, 고객에게 무엇을 어떻게 옮길지는 직원이 거른다. 그래서
에이전트의 책임은 "고객에게 보여도 되는 문장만 만드는 것"이 아니라 **직원이 거를 수 있도록
재료의 성격을 함께 알려주는 것**이다(§7). 내부용 자료도 답변에 쓰고, 고객에게 그대로
옮기면 안 되는 것은 주의로 알린다 — 코드가 막지 않는다.

### 하지 않는 것

- **고객이 직접 쓰지 않는다.** 대고객 채널이 아니다.
- **수치·적합성 계산을 하지 않는다.** 고객 관련 판정·계산은 전략제안(strategy_agent)이
  하고, 대화형은 그 산출을 받아 말한다 — 같은 판정을 두 번 구현하면 화면과 대화가 다른
  값을 말하게 된다.
- **화면의 계산값을 대화로 바꾸지 않는다.** 수정 요청은 AI 가 쓴 산문에만 열려 있다.
- **지식베이스에 없는 기준을 만들지 않는다**(루트 「판단의 근본」). 재료가 없으면 없다고
  답한다.

### 상위 요건과 다른 문서

상위 요건은 `07_에이전트_기능정의/01` 의 **② 영업 중 — 채팅형 인터페이스** 장이다(반론
대응 · 판별 질문 → §5 · 계산기 · 가능 여부 즉시 확인 → §13). 그 장이 정한 **즉답 카드
양식**은 §5 의 결정으로 요건에서 내렸다 — 아래 「양식은 요건이 아니다」. ① 영업 전 브리핑
장은 전략제안 소관이며, 그중 요소 3(고객이 모르는 자기 현황)·요소 6(하지 말 것)만 대화형이
위임받았다 — 자기 현황은 답변 재료로(§3), 요소 6 은 금지·주의 안내로(§8).

`docs/REQUIREMENTS.md` 는 전체 서비스 요건이고, 그중 화면·섹션 정의(그 문서 1.1 대응표 ·
2장 ①~⑨ 섹션 정의와 생성 주체 · 3~7장)는 전략제안 요건이라 대화형 근거로 인용하지 않는다.
원문·타 문서와 어긋나면 대화형 기준은 이 문서다.

> **번호 표기**: 이 문서에서 `§n` 은 **이 문서의 절**이다. 다른 문서의 절을 가리킬 때는
> 문서 이름을 함께 적는다(예: "REQUIREMENTS 7장"). 저장소에는 번호 축이 셋 섞여 있다 —
> `①~④`(영업 시점) · `①~⑨`(브리핑 화면 섹션) · 폴더 번호.

## 2. 한 턴이 처리되는 순서

한 턴의 입력은 넷이다 — **이번 질문 · 이전 대화 맥락 · 지금 열려 있는 고객(있을 수도 없을
수도 있다) · 상담 세션 구분자**. 고객 화면이 열려 있는지가 답을 가른다(§3).

턴은 세 가지로 끝난다: **답변** · **되묻기**(§5) · **직전 제안의 확인·연계**(§10). 아래는 답변
턴의 순서다.

1. **질문 이해** — 질문과 이전 대화 맥락으로 무엇을 원하는지 정한다. 후속 질문("그럼 안
   된다고 하면요?")은 이전 턴들의 내용을 이어받아 해석한다.
2. **근거 수집** — 답에 필요한 근거를 도구로 모은다. 질문에 따라 도구 하나만 부를 수도,
   여러 개를 차례로 부를 수도 있다("수수료가 얼마고 뭐라고 말하지" → 확정값+고객재료+화법).
   어떤 도구를 어떤 질의로 몇 번 부를지는 LLM 이 정하고, 부를 수 있는 도구 목록·호출
   상한·같은 호출 반복 차단은 코드가 정한다. 모은 근거는 그 턴의 **근거 목록**에 쌓인다(이 문서에서 «원장»이라 부른다).
3. **답변 작성** — LLM 이 원장의 근거와 대화 맥락만으로 질문에 답이 되는 답변을 쓴다
   (§4·§5). 근거가 0건이면 지어내지 않고 찾지 못했다고, 무엇이 있는지와 함께 답한다.
4. **답변 점검** — 코드가 답변을 근거·관계 선언과 대조한다(§6). 걸린 생성문은 화면에
   내보내지 않는다.
5. **화면 연계 제안** — 답변이 직원이 이어서 쓸 단말 화면을 가리키면 연계를 제안하고,
   연계는 다음 턴의 확인 뒤에 한다(§10).

질문이 모호해 답의 갈래가 갈리면 3단계에서 답변 대신 **판별 질문**으로 턴이 끝난다(§5).
되묻기 턴에는 5단계를 붙이지 않는다. 직전 턴의 제안에 답하는 턴("네"·"아니요")은 근거를
모으지 않고 바로 연계·취소로 간다(§10).

상담이력은 intent 와 무관하게 **진입점 한 곳**에서 턴마다 기록한다 — 새 기능이 추가돼도
기록이 빠질 수 없다. 단방향인 것은 **쓰기**다 — 대화형만 쓰고 전략제안은 읽기만 한다.
대화형은 자기가 남긴 기록을 다음 상담에서 재료로 다시 읽는다(§3).

## 3. 답변의 재료 — 무엇을 근거로 답하나

- **에이전트가 할 수 있는 일 = 등록된 도구 목록이다.** 새 종류의 지식·재료로 답하게 하려면
  도구 하나를 추가한다 — 의도 enum·분기표·노드를 함께 늘리지 않는다. 같은 재료를 두 경로로
  구현하지 않는다.
- 재료는 10종이다: 화법 · 제도 확정값 · 업무 절차 · **단말 화면번호** · **비대면 채널 경로** ·
  고객군 정의 · 관리 방법론 · 현장 관찰 · 열려 있는 고객의 브리핑 재료 ·
  **그 고객과의 지난 상담 기록**. 절차·화면·채널이
  따로 있는 이유는 묻는 것이 다르기 때문이다 — 절차는 "어떻게 처리하나"(순서·주의),
  화면은 "직원이 단말에서 어느 화면인가"(번호·화면명), 채널은 "고객이 앱·웹에서 어느
  메뉴인가"다. 셋을 하나로 묶으면 직원이 단말에서 할 일을 고객에게 시키게 된다.
- 고객 재료의 계산은 strategy_agent 산출을 그대로 쓴다 — 같은 판정을 두 번 구현하지 않고,
  화면과 다른 값을 말하지 않기 위해서다.
- **지난 상담 기록도 재료다.** 저작된 지식 카드가 아니라 에이전트가 턴마다 남긴 운영
  기록이지만(§2), "지난번에 무슨 얘기 했지"에 답하려면 그것 말고 근거가 없다. 재료가
  없는 질문에 LLM 은 답을 만들어낸다 — 이 재료가 없던 동안 그 질문은 능력 안내로 끝났고,
  다음 턴 답변에 "이전 대화 내용은 기억하지 못해요"가 따라 나왔다(사실도 아니었다).
  다만 기록은 **"그때 무슨 얘기를 했나"의 근거이지 현재 기준 값의 근거가 아니다** — 지난
  상담의 안내가 지금도 맞다는 보장이 없으므로 시효 표시를 달고 나온다(§7 · §9).
- **고객 화면이 닫혀 있으면 고객 관련 기능은 답하지 않는다.** 브리핑 질의·수정·LMS 화면 연계는 어느
  고객인지가 있어야 성립한다 — 없으면 지어내거나 일반론으로 넘어가지 말고 "고객 화면을
  먼저 열어달라"고 답한다. 지식 질의응답과 화법 코칭은 고객 화면 없이도 답한다.
- 도구는 근거 또는 "못 찾았다"를 돌려준다. 도구가 억지로 뭔가 만들어내는 경로는 두지
  않는다 — 원장이 비면 정직하게 없다고 답한다.
- LLM 이 보는 후보는 검증을 통과해 적재된 카드뿐이다. LLM 이 자유 텍스트로 근거를
  만드는 경로를 추가하지 않는다.
- **모든 답에 출처를 밝힌다.** 답변 내용에 영향을 준 재료는 전부 출처에 실린다 — 지식
  카드뿐 아니라 열려 있는 고객의 브리핑 재료도, 「하지 말 것」 가드와 대안 화법도 그렇다.
  출처에 없으면 화면은 "근거 없음"이라고 말하고, 직원은 근거 없이 나온 말로 읽는다.
  **역할을 함께 싣는다** — 답이 그 재료에서 «나온» 것(근거)과 표현을 «제한만» 한 것(§8 의
  고객 상태 가드)은 다른 사건이고, 화면도 갈라 보여준다. 한 목록에 섞으면 화면번호 하나를
  물은 답에 수익률 관리 카드가 근거로 나란히 서고, 그러면 직원은 답이 어디서 나왔는지
  읽어낼 수 없다. 관련도는 **검색으로 온 재료에만** 있다 — 없는 재료에 그 칸을 비워
  두지 말고 아예 띄우지 않는다(관련도 0 과 관련도를 잴 수 없는 재료는 다르다).
  사내 파일명은 출처가 아니다 — 원천 문서 → 원문 표기 →
  추출지식 절 순으로 물러서고, 끝내 없으면 지어내지 않고 "출처 미상"이라고 말한다. 출처
  문자열을 만드는 곳은 하나다.
- **화면의 계산값은 대화로 고칠 수 없다.** 브리핑 수정 요청은 AI 가 쓴 산문(제안 문장·
  근거 해설·카드 문구)에만 열려 있다. 평가금액·수익률·상품·전략 선정처럼 코드가 결정론으로
  계산한 값은 거절하고 **왜 대화로 못 고치는지** 알려준다. 편집 가능한 항목인지 애매하면
  거절한다. 고친 내역은 기록으로 남긴다.
- **평가금액·문제상황은 판단 재료다.** 직원이 묻지 않았는데 답변에 선제적으로 끼워 넣지
  않는다 — 화법 코칭을 물었는데 평가금액이 따라 나오면 안 된다. 명시적으로 물은 질문
  ("평가금액 얼마야?" · "왜 관리 대상이야?")에는 그 값·정의 자체가 질문이므로 답한다.

### 고객 정보 질의응답 — 되어야 하는 것

직원이 «열려 있는 고객»에 대해 묻는 질문. 재료는 `customer` 도구 하나이고, 값은 전부
strategy_agent 산출(`engine.prepare` · `agent.propose`)에서 온다 — 같은 판정을 두 번
구현하지 않고 화면과 다른 값을 말하지 않기 위해서다.

**답해야 하는 질문 네 갈래.** 재료에 없으면 답이 나올 수 없으므로, 아래는 곧 재료 요건이다.

| 갈래 | 직원이 묻는 말 | 답에 있어야 하는 것 |
|---|---|---|
| ① 값 | "평가금액 얼마야" · "고유계정대 얼마야" · "만기 언제야" · "올해 얼마 넣었어" | 그 값 **하나**. 금액을 물으면 금액, 비중을 물으면 비중 |
| ② 왜 이 고객인가 | "왜 관리 대상이야" · "이 고객 뭐가 문제야" | 성립 요건 + 그 요건이 왜 문제인지(세그먼트) + 판단근거 |
| ③ 무엇을 하나 | "뭐 제안하면 돼" · "왜 이 상품이야" | 화면에 뜬 제안·근거해설과 **같은 내용** |
| ④ 하면 안 되는 것 | "주의할 거 있어" (묻지 않아도 §8 가드가 붙는다) | 지식베이스에 있는 금지·주의만 |

**지켜야 할 것.** 전부 실제로 깨졌던 자리다.

- **금액과 비중을 둘 다 답할 수 있어야 한다.** 재료에 비중만 있으면 "고유계정대 얼마야"에
  "8%예요, 금액은 재료에 없어요"가 나간다. 전략 로직이 쓰는 `port` 4분류는 정수 비중
  요약이고 여러 자산군을 한 칸에 접는다 — 원장 값(`Profile.assets`)을 함께 싣는다.
- **같은 항목이 재료 안에서 두 값이 되면 안 된다.** 4분류 요약은 반올림이라 원장의 7.7% 가
  8% 로 나가고, 두 줄이 함께 실리면 어느 쪽을 인용해도 다른 줄과 어긋난 답이 된다.
  파생 뷰(3분류)는 원장에서 뽑는다.
- **한 항목에 여러 건이면 전부 답한다.** 만기가 대표적이다 — 예금과 GIC 의 만기가 서로 다른
  고객이 있어서, 가장 가까운 한 건만 답하면 나머지가 없는 것이 된다. 요건 판정·배분액이
  «가장 가까운 한 건»을 쓰는 것과, 재료가 «전부»를 들고 있는 것은 다른 이야기다.
- **재료 안 값에서 계산해 새 값을 만들지 않는다.** 잔여일수만 싣고 날짜를 빼면 LLM 이
  기준일에서 더해 날짜를 말한다. 그 계산은 근거가 아니고, 틀려도 수치 검사에 안 걸린다
  (조각 숫자가 재료 어딘가에 있으면 통과한다) — 답해야 하는 형태의 값을 재료에 싣는다.
- **묻지 않은 값을 덧붙이지 않는다.** 다만 «좁히는 것»과 «빠뜨리는 것»은 다르다(위 다건 항목).
- **출처는 고객 원장이지 지식 카드가 아니다.** 검색으로 온 재료가 아니므로 관련도도 없다.
  카드처럼 표기하면 계좌에 그냥 들어 있는 값이 어딘가에서 찾아온 자료처럼 읽힌다.
- **재료가 없으면 없다고 답한다.** 지어내지도, 일반론으로 넘어가지도 않는다.

**아직 답할 수 없는 질문 — 어디서 끊겼는지가 다르다.**

값이 대화형까지 오는 경로는 넷이다: ① 원본 xlsx → ② `customers.json`(원장) →
③ `Profile`(매핑) → ④ 브리핑 재료. **원장에 컬럼이 있는 것과 답할 수 있는 것은 다르다** —
`Profile` 이 접지 않으면 ③에서 끊겨 대화형은 그 값을 본 적이 없다. 아래 표의 «끊긴 곳»은
그 지점이고, 고칠 자리도 거기다.

| 질문 | 끊긴 곳 |
|---|---|
| "무슨 상품 들고 있어" · "수익률 나쁜 상품 뭐야" · "판매중단된 거 있어" | ③ — 원장 `products`(보유상품 개별 종목)를 `Profile` 이 자산군별 합계로만 접는다 |
| "지난번에 무슨 얘기 했어" | ③ — 원장 `history` 를 아무도 안 읽는다. `consult_history` 는 이 에이전트가 남긴 세션 기록만 읽어서, 엑셀에 적힌 과거 상담은 비어 있다 |
| "동연령대랑 비교하면" | ③ — 원장 `peer`. 화면 ④ 는 아직 `data/top_holdings.json` 자리표시자를 쓴다(고객별 값이 아니다) |
| "최근에 거래한 적 있어" | ③ — 원장 `activity`(최근 매매일·매매 횟수·ETF 보유 이력) |
| 배지 4종(판매중단펀드·ISA만기·연금개시 미개시·이탈위험관찰) | 요건(`CONDS`)이 아니다 — 지식베이스에 판정 근거가 확인돼야 세운다. 값을 «답하는» 것과 그것으로 고객을 «뽑는» 것은 다른 결정이다 |

ISA 만기자금·연도별 납입 이력은 한동안 같은 이유(③)로 막혀 있다가 지금은 연결돼 있다
(`Profile.isa` · `paid_by_year`). ISA 는 **IRP 계좌 밖의 돈**이므로 보유 현황과 갈라 적는다 —
섞으면 IRP 잔액이 부풀어 보인다.


## 4. 답변 내용의 기준 — 근거에서 나온 것만 · 금지 표현

답변의 내용은 원장의 근거(지식 카드와 고객 브리핑 재료)에서 나온다. 그러나 **원문을 그대로
옮길 의무는 없다** — LLM 은 질문 의도에 맞게 원문의 내용을 풀어 쓰고, 여러 재료를 조합한다. 지켜야
하는 것은 문장이 아니라 뜻이다.

- 근거에 없는 수치·상품명·요건을 만들지 않는다.
- 값과 그 값이 성립하는 조건의 짝을 바꾸지 않는다 — "이하 16.5% / 초과 13.2%" 를
  "초과면 16.5%" 로.
- 원문의 단서·전제(결정세액 한도, 합산 기준 등)를 떼고 값만 옮겨 뜻을 넓히지 않는다.

이 세 가지를 "원문 문장을 그대로 실어라"로 지키게 하면 답변이 인용문 나열이 된다. 대신
**데이터가 관계를 선언하고**(값↔조건 쌍 · 알려진 오답 패턴 — `../knowledge/CLAUDE.md`)
**코드가 그 관계로 대조한다**(§6). 원문 문장을 통째로 실으라는 요구는 이 기준에 없다.

**금지 표현.** 근거 안에서 쓴 문장이어도 아래는 답변에 넣지 않는다 — 직원이 상담 중에
고객에게 그대로 옮길 수 있는 말이기 때문이다.

- **실적배당형 상품의 수익을 확정적으로 약속하지 않는다.** 원금손실 가능성이 있는 상품의
  과거 수익률·기대수익을 "받게 된다"로 말하지 않는다. 근거 카드에 수익률이 있다는 것은
  그 수치를 인용해도 된다는 뜻이지 보장해도 된다는 뜻이 아니다.
- **제도·요건을 임의로 넓히거나 추정하지 않는다.** "아마 될 것 같다"는 답을 만들지 않는다 —
  확인이 필요하면 확인이 필요하다고 답한다.

**이전 대화는 이번 질문을 해석하는 데만 쓴다.** 답은 이번 질문에 대해서만 쓴다 — 앞 턴에서
못 답한 것을 뒤늦게 사과하거나, 무엇을 기억하는지·못 하는지를 답변에 적지 않는다. 지난
대화 내용 자체가 이번 질문이면 그건 재료로 원장에 실려 온다(§3). 재료가 없는 것에 대해
에이전트 자신의 사정을 설명하는 문장은 답이 아니고, 사실과 다를 수도 있다 — 화면번호를
물은 턴에 "이전 대화 내용은 제가 기억하지 못해요"가 따라 나온 적이 있다(대화 맥락은
프롬프트에 실려 있었다).

내부용 자료는 금지가 아니다 — 답변에 쓰되 고객에게 그대로 옮기지 말라는 주의를 함께
알린다(§7).

## 5. 답변 적절성 — 질문에 답이 되는가

**틀리지 않은 답과 질문에 답이 되는 답은 다르다.** §6 의 점검은 전부 "틀린 것을 막는"
검사라 적절성을 보증하지 못한다 — 적절성은 근거를 고르는 단계(§2-2)와 문장을 쓰는
단계(§2-3)에서 지켜야 한다. 주 기능이 지식 질의응답이므로 이 절의 요건은 §6 의 점검과
같은 비중으로 지킨다.

**근거가 질문의 실제 의도에 맞아야 한다.** 주제어만 겹치는 카드로 답하지 않는다 — "연금
개시를 앞둔 고객에게 뭘 안내하나"에 "개시가 이르다고 거절하는 고객" 카드로 답하면 단어는
맞고 답은 틀리다. 고른 근거가 질문에 답이 되는지 판정하고, 애매하면 그 근거를 버린다.
**틀린 답을 주느니 없다고 하는 편이 낫다.** 이 판정은 재료 종류를 가리지 않는다 — 화법만의
장치가 아니다.

**모호하면 되묻는다(판별 질문).** 질문만으로 답의 갈래가 갈리는데 어느 쪽인지 알 수 없으면,
한쪽을 골라 답하지 말고 되묻는다 — "실물이전"이 타행→당행인지 당행→타행인지에 따라 절차가
다른데 아무 쪽이나 답하면 직원은 그게 다른 절차인 줄도 모른다. 되묻기는 답을 미루는 것이
아니라 **틀린 답을 막는 것**이다(07/01 ② 판별 질문).

- **되묻는 경우**: 지식베이스에 갈래가 실제로 존재하고(A 절차와 B 절차, 계좌 유형별로 다른
  값), 질문·대화 맥락·열린 고객 화면 어디에도 어느 쪽인지 정할 근거가 없을 때.
- **되묻지 않는 경우**: ① 맥락으로 추측이 서면 되묻지 말고 **전제를 밝히고 답한다**
  ("타행에서 당행으로 가져오는 경우로 안내드릴게요"). 상담 중에 읽는 화면이라 한 번 더
  묻는 비용이 직원 쪽에 크다. ② 근거를 못 찾은 것은 모호한 것이 아니다 — 그건 없다고
  답한다(이 절 마지막). ③ 답이 갈리지 않는 질문에 확인차 되묻지 않는다.
- **선택지를 제시한다.** "무엇을 원하세요?" 처럼 열어놓고 묻지 않는다 — 직원이 무엇을
  답해야 할지 다시 생각해야 한다. 지식베이스에서 실제로 갈리는 갈래를 보여주고 고르게 한다.
- **되물은 다음 턴의 짧은 답은 그 질문의 답이다.** "2번째꺼"·"후자"·선택지 문구 일부는
  선택지를 고른 것이므로, 원래 질문과 고른 갈래를 합쳐 그 자리에서 답한다. 이런 답은
  연계 확인(§10)의 "네"와 닮아 오분류될 수 있는데, 확인할 제안이 걸려 있는지는 코드가
  아는 값이다 — 제안이 없고 직전 턴이 되물음이면 분기표가 분류와 무관하게 계획 루프로
  보낸다(`routing.route_intent`, 지워진 gap 19).
- **연속으로 되묻지 않는다.** 되물었는데도 여전히 모호하면 가장 가능성이 높은 갈래를
  전제로 밝히고 답한다. 되묻기 횟수의 상한은 코드가 정한다 — 확인만 반복하는 턴이 이어지면 직원은
  에이전트를 쓰지 않게 된다(§10 이 매 턴 연계를 제안하지 않는 것과 같은 이유).
- 되묻기는 §10 의 연계 확인과 다르다. 되묻기는 **답변 전에 갈래를 정하는 것**이고, 연계
  확인은 **화면을 열기 전에 승낙을 받는 것**이다. 되묻기 턴에는 연계 제안을 붙이지 않는다.

**질문 유형이 답의 형태를 정한다.** 근거가 맞아도 형태가 어긋나면 답이 아니다(값을 물었는데
화법이 나오거나, 할 말을 물었는데 제도 설명만 나오는 것).

| 질문 | 답에 들어가야 하는 것 |
|---|---|
| 값·한도·요건 ("세액공제 한도 얼마야?") | 값 + 그 값이 성립하는 조건 + 기준시점 + 출처 |
| 업무 절차 ("계약이전 어떻게 처리해?") | 처리 순서 + 화면번호·채널 + 걸리는 주의 |
| 화면번호 ("포트폴리오 운용현황 조회 화면번호?") | 화면번호 + 그 화면이 무엇을 하는 화면인지 |
| 비대면 경로 ("고객이 앱에서 직접 하려면?") | 채널별 메뉴 경로 + 그 채널에서 되는지 안 되는지 |
| 고객군 정의 ("편중 고객 왜 관리 대상이야?") | 선정 조건 + 왜 문제인지 |
| 판단 기준 ("어떤 고객부터 관리해야 하나") | 판단 기준 + 그 기준의 도출 근거 |
| 화법 ("뭐라고 말하지?") | 고객에게 그대로 할 수 있는 말 + 왜 그렇게 접근하는지 |
| 고객 현황 ("이 고객 평가금액 얼마야?") | 물어본 값 (묻지 않은 값을 덧붙이지 않는다 — §3) |

**누구에게 하는 말인지 구분한다.** 답변은 기본적으로 **직원에게 코칭하듯** 쓴다 — 고객은
3인칭으로 부르고("고객에게는 ~"), 보고서체가 아니라 상담 중에 빠르게 읽을 수 있는 말투다.
그 안에서 **고객에게 그대로 읽어줄 대사**는 따로 구분되게 쓴다. 직원이 어디까지가 자기에게
하는 설명이고 어디부터가 고객에게 할 말인지 분간되지 않으면, 직원이 코칭 문장을 고객에게
그대로 읽는 일이 생긴다.

**고객 대사를 그대로 던진 질문도 같은 형태로 답한다.** "증권사는 수수료 무료라던데요,
뭐라고 답하지?"는 화법 코칭 질문이다 — 재료도 같고(화법) 형태도 같다. 상담 중에 바로 읽을
수 있어야 하므로 고객에게 할 말이 답 안에 있어야 하지만, 그것은 위 표의 화법 요구
("고객에게 그대로 할 수 있는 말 + 왜 그렇게 접근하는지")가 이미 말하고 있다.

### 양식은 요건이 아니다

한때 이 절은 고객 대사를 던진 질문에 **즉답 카드 양식**(고객 발화 / 조건 분기 / 완성 대사 /
추가 논거 / ⚠ 사전 고지 / 근거·기준시점 / 신뢰 표시)으로 답하라고 요구했다. 07/01 ② 가 그
양식을 그린 것을 그대로 요건으로 옮긴 것이었다. **2026-08-25 에 내렸다.**

내린 이유는 양식 자체가 답을 나쁘게 만들었기 때문이다. 칸을 채우려면 카드에서 칸에 맞는
조각을 뽑아야 하는데, 카드가 어긋나면 **빈 칸을 채우려고 엉뚱한 조각이 그대로 박힌다** —
직원 업무 가이드 카드가 잡히자 그 카드의 트리거 예시("고객이 어떤 상품을 갖고 있는지 어떻게
확인하나요")가 `[고객 발화]` 칸에, 카드 제목("상품 보유 현황 확인")이 `[완성 대사]` 칸에
들어갔다. 산문이면 "이 질문에는 준비된 자료가 없다"고 쓸 수 있는 자리에서, 양식은 무엇이든
채워 넣은 채로 완성된 카드처럼 보인다.

양식을 유지하려면 그 양식 전용의 조립 경로가 필요하고, 그 경로는 계획 루프 밖에 있게 된다 —
실제로 적합성 판정(§5)·재료 성격 표시(§7)·답의 형태 요구(§5 표)가 하나도 걸리지 않았다.
**답의 양식을 위해 답의 품질 장치를 우회하지 않는다.**

07/01 ② 의 양식이 담고 있던 것들은 버리지 않았다 — 완성 대사는 화법 요구로(§5 표),
⚠ 사전 고지는 조건부 주의로(§7), 근거·기준시점과 신뢰 표시는 재료 성격 표시로(§7) 남아
있다. 사라진 것은 **칸**이다.

**부분만 근거가 있으면 있는 만큼 답한다.** 질문이 여러 가지를 묻고 그중 일부에만 근거가
있으면, 답할 수 있는 부분을 답하고 나머지는 "그 부분은 준비된 자료가 없다"고 짚는다. 근거
없는 한 조각 때문에 답 전체를 버리지 않는다.

**여러 재료를 묶을 때는 각 재료가 무엇을 뒷받침하는지 드러나게 쓴다.** "수수료가 얼마고
뭐라고 말하지"의 답은 값과 대사가 뒤섞인 한 문단이 아니라, 값이 근거이고 대사는 그 값을
근거로 삼는다는 것이 드러나는 형태다.

**못 찾았으면 무엇을 갖고 있는지 알려준다.** "없습니다"로 끝내면 직원이 어떻게 다시 물어야
할지 모른다 — 어떤 종류의 재료를 갖고 있는지, 그리고 **무엇을 어떤 말로 찾아봤는지** 함께
말해 다음 질문이 가능하게 한다. 찾아본 내역이 없으면 "분명 있는 지식인데 왜 못 찾지?"에
아무도 답할 수 없다 — 진단이 화면에서 끝나야 한다(§11 과 같은 이유).

**계획이 질의를 잘못 골랐다고 지식베이스에 있는 답이 사라지지 않는다.** 도구가 근거를 못 찾으면
직원의 원문 질문으로 한 번 더 찾는다. 근거를 0건으로 둔 채 계획을 끝내지도 않는다 — 다른
도구를 써 볼 기회 없이 '근거 없음'으로 끝나면, 재료가 없는 것이 아니라 **고르기를 실패한
것**이 없다고 답해진다.

## 6. 답변 점검 — 코드가 근거와 대조한다

생성된 답변은 내보내기 전에 코드가 검사한다. 검사의 재료는 원장(이번 턴에 모은 근거)과
지식 데이터의 관계 선언이다.

| 검사 | 재료 | 걸리면 |
|---|---|---|
| 근거 밖 수치·상품명 | 원장 텍스트 · 등록 상품명 | 그 생성문을 내보내지 않는다 |
| 값–조건 짝 오류 | 데이터의 값↔조건 쌍 · 오답 패턴 | 그 생성문을 내보내지 않는다 |
| 답변과 관련 있는 주의 누락 | 데이터의 주의 역할·적용 조건(§7) | 빠진 주의를 덧붙인다 |

**판정 불가를 위반으로 바꾸지 않는다.** 관계 검사는 문자열 대조라, 답변이 조건을 다른 말로
풀어 쓰면 아무 말도 하지 않는다. 그건 통과가 아니라 판정 불가이고, 판정 불가를 위반으로
다루면 맞는 답이 막힌다 — **검증기가 옳은 문장을 거부하는 것은 틀린 문장을 통과시키는
것보다 나쁘다.** 직원은 왜 막혔는지 알 수 없고, 그 다음부터는 에이전트를 믿지 않는다.

- 요건은 "걸린 생성문이 화면에 나가지 않는다"이다. 그 뒤의 처분(재생성 · 근거 원문 제시)은
  구현이 정하되, 틀린 문장이 나가는 선택지는 없다.
- 검증기는 수치·상품명·관계만 보고 **톤도 형태도 적절성도 보지 않는다** — 그쪽은 생성
  지시(§4 금지 표현 · §5 형태·화자)와 코드가 붙이는 경고로 지킨다. 점검을 통과했다는
  것이 좋은 답이라는 뜻은 아니다.
- 검사의 커버리지는 데이터의 관계 선언 범위와 같다. 선언이 없는 카드의 오짝은 못 잡는다 —
  그래서 관계 저작이 검증의 전제 조건이다(`../knowledge/CLAUDE.md` 의 이행 순서).

## 7. 주의·표시 — 관련 있을 때만 붙인다

표시는 무조건 붙이는 것이 아니다. **답변 내용에 실제로 적용되는 주의만 붙이고, 무관한 것은
생략한다.** 직원이 상담 중에 읽는 화면이다 — 무관한 경고가 늘어설수록 관계있는 경고를 읽고 넘어갈
확률이 올라간다. 판단의 근거는 데이터의 선언이다(숫자가 있는지 따위로 추론하지 않는다).

| 갈래 | 무엇 | 언제 붙나 |
|---|---|---|
| 재료 성격 표시 | 어느 자료에서 온 말인지(신뢰 등급, 아래) · 시효 민감 · 확인 필요 상태 | 그 재료를 근거로 쓴 답변에는 관련 있는 것으로 본다 |
| 조건부 주의 | "~한 경우에는 안 된다" 류 단서 | 답변이 다루는 값·고객 상태·주제에 그 조건이 걸릴 때 |
| 저작 메모 | "자료 간 표기 상충 · 팀 논의 필요" 류 문서 검증 기록 | 직원에게 띄우지 않는다 — 지식베이스 관리용이다 |

이 갈래는 데이터가 선언한다 — 주의·비고 필드는 `{role, text}` 항목이고, role 은
caution(표시로 강제) / info(답변 재료로만 실림) / authoring(직원에게 미표출)이다
(`knowledge/kinds.json` · 분류 공정은 `build_kb.role_entries` + config 예외표).
caution 이 **언제** 걸리는지(적용 조건)의 선언은 아직 없다 — §12 gap 7 의 남은 부분이다.

**신뢰 등급**: 어느 자료에서 왔는지가 곧 그 말을 얼마나 단정해도 되는지다(07/01 ② 신뢰
표시). 종류를 가리지 않고 모든 답변에 붙는다. 등급은 문서 레지스트리가 갖고 있고 답변은 그것을 그대로 옮긴다 — 본부 공식 자료 /
영업점 현장 노하우(본부 확정 지침 아님) / 대외 공개 자료(고객에게 그대로 안내 가능) /
직원 교육자료. 현장 노하우가 본부 지침으로 읽히면 그게 곧 잘못된 안내다.

**내부용 자료의 주의**: 카드에는 "고객에게 그대로 안내해도 되는가"(`customer_facing`,
원문의 ▶·⭕ 표시) 선언이 있다. 에이전트는 직원용이므로 내부용 자료도 답변 재료로 쓴다.
다만 그 내용이 답변에 실리면 "이 내용은 고객에게 그대로 안내하지는 마세요" 류의 주의를
함께 준다. **막지는 않는다** — 무엇을 고객에게 옮길지는 직원이 정하고, 에이전트는 판단에
필요한 표시를 주는 데까지가 몫이다.

## 8. 금지·주의 안내 — 이 고객에게 하면 안 되는 것

고객 상태에 걸린 금지·주의를 답변과 함께 띄운다(07/01 ① 요소 6 위임분).

"지식베이스에 없는 기준은 만들지 않는다"(루트 「판단의 근본」)가 원칙이다. 금지 문장은
전부 지식베이스가 갖고 있고, 코드는 고객 요건 → 재료의 연결만 갖는다. 재료가 없는 요건에는
아무것도 띄우지 않는다.

- 고객 화면이 열려 있으면 그 고객 상태에 걸린 주의는 **코드가 판단해 띄운다** — LLM 이 고객
  재료를 찾아봤는지에 의존하지 않는다. 고객 상태는 코드가 이미 아는 값이다.
- 금지만 알려주면 행원은 할 말이 없어진다. 지식베이스에 대안(민감 응대 화법)이 있으면 함께
  올린다.

### 운영 판단으로 정한 금지 규칙 — 관리대장

지식베이스 유래 금지와 별개로, **데이터를 근거로 서비스 설계자가 직접 판단해 내린 금지
규칙**이 있다. 출처가 다르므로 구분해 표기하고, 판단의 근거와 이력을 이 대장에 남긴다.
새 운영 판단이 생기면 행을 추가한다 — 코드에만 넣고 여기 안 적으면 나중에 "왜 금지인지"를
아무도 추적할 수 없다.

| 규칙 | 판단 근거 | 등록 | 집행 |
|---|---|---|---|
| 연금수령 개시 계좌에는 추가납입을 권유하지 않는다 | 데이터 기반 운영 판단. 뒷받침: 방법론 59 "연금개시 → 추가입금 불가", 07/01 ① 요소 6, 현장 실패 사례(강현애) | 2026-08-21 (REQUIREMENTS 7장 신설) | 요건 판정·브리핑 재료 생성에서 차단(strategy_agent) — 대화형은 그 재료를 받으므로 권유 문장이 근거를 잃는다 |

## 9. 시효성 수치 — 최신화하고, 조건 판정을 거친다

금리·제도처럼 시간이 지나면 틀리는 수치는 현재값으로 최신화하고, 그 수치에 걸린 주장
("~보다 높다" 등)은 성립 조건을 판정해 깨졌으면 격리하거나 확인을 요구한다. 화법만이
아니라 시효성 수치가 실리는 **모든 재료**(절차·노하우 포함)에 적용한다.

- 원문(quotes·source_text)은 어떤 경우에도 고치지 않는다(루트 절대 규칙 1). 최신화는 파생
  텍스트에서 한다. 원문에만 수치가 있으면 "원문 X · 현재 Y" 참고 표시를 함께 보여준다.
- 어떤 수치가 슬롯이고 어떤 주장에 어떤 조건이 걸리는지의 **선언은 데이터, 판정은
  코드**다. 판정 근거가 시스템에 없는 주장(타사 값 등)은 지어내지 않고 확인 요구 경고를
  붙인다.
- 격리·판정은 적재 한 곳에서 한다 — 소비처마다 거르게 두면 언젠가 한 곳이 빠진다.
- 제도 상수·시뮬레이션 가정치처럼 "현재 값"이라는 것이 없는 수치는 바꾸지 않는다.
- **지난 상담 기록은 최신화 대상이 아니다.** 그때 그렇게 안내한 것이 사실이라 고칠 것이
  없다 — 대신 그것이 지난 기록임을 표시해, 답변이 그 값을 지금 기준으로 말하지 않게
  한다(§3 · §7). 최신값이 필요하면 그 값을 가진 재료를 따로 부른다.

## 10. 화면 연계 — 제안 · 확인 · 파라미터

답변이 직원이 단말에서 이어서 할 일을 가리키면(업무 절차 안내의 화면번호, 고객에게 보낼
문구의 LMS 발송 화면 등), 그 화면으로 바로 갈 수 있게 **연계를 제안**한다. 실제 작업은
직원이 그 화면에서 한다 — 에이전트는 화면을 열어줄 뿐 작업을 대신 수행하지 않는다.

- **제안 → 확인 → 연계.** 답변 끝에 "이 화면 연계해드릴까요?"를 붙이고, 직원이 승낙하면
  그 화면을 여는 URL 을 준다. 승낙 없이 열지 않는다.
- **제안 여부는 규칙이 정한다**(LLM 아님). 답변이 실제로 화면을 가리키고 그 화면을 열
  정보가 갖춰졌을 때만 붙인다 — 매 턴 "연계해드릴까요?"가 붙으면 직원이 읽지 않게 되고
  확인 절차가 의미를 잃는다. **"가리킨다"는 답변이 그 화면번호를 인용했다는 뜻이다.**
  답변 안에 고객에게 할 말이 들어 있다는 것은 화면을 가리키는 신호가 아니다 — 화법 코칭
  답변이면 거의 항상 참이라, 그걸 신호로 삼으면 매 턴 붙는다. 문구를 보내려는 직원은
  그렇게 말하고("이 문구로 LMS 보내줘"), 그 요청이 발송 화면 연계를 제안한다.
- **링크는 단말 연동 규격을 따른다.** 단말 화면은 커스텀 스킴 딥링크로 연다 —
  `mystar-link://scnNo=0612604&mode=D`. `?` 없이 스킴 뒤에 바로 `키=값` 이 오고 구분자는
  `&` 다. `scnNo` 는 화면호출번호 7자리 또는 단말화면번호 11자리이며, 지식베이스의 화면번호
  표기(`[06-12-604]`)에서 구분자를 뺀 것이 7자리다. `mode` 는 운영 `O`·스테이징 `S`·
  개발 `D` 이고 **지금은 개발이다**(`docs/DEMO_STATUS.md`). 자릿수가 맞지 않는 번호로는
  링크를 만들지 않는다 — 단말이 엉뚱한 화면을 열거나 아무것도 열지 못한다.
- **규격에 없는 파라미터는 싣지 않는다.** 링크에 들어가는 것은 `scnNo`·`mode` 뿐이다.
  고객 식별자·발송 문구를 단말이 어떤 이름으로 받는지 정해지지 않았고, 받지도 않는 키를
  붙이면 단말이 링크를 통째로 못 읽을 수 있다 — 그 값들은 직원이 열린 화면에서 입력한다.
  **채우지 않은 값을 채웠다고 말하지 않는다.** 링크가 싣지 못하는 값(발송 문구)은 직원이
  화면에서 넣도록 답변에 함께 준다. 단말 규격이 파라미터를 정의하면 그때 싣는다.
- **파라미터는 근거에 있는 값으로만 채운다**(§4 와 같은 기준). 화면번호는 근거 카드에 있는
  것을 쓴다. 없는 화면번호로 링크를 만들지 않는다 — 직원이 엉뚱한 화면에서 작업하게 된다.
  열 화면을 특정하지 못하면 연계 대신 화면번호만 안내한다.
- **화면으로 넘기는 문구도 답변과 같은 기준을 따른다**(§4). 여기서 코드가 거부하는 것은
  **아직 실제 콘텐츠로 확정되지 않은 더미 문구** 하나뿐이다 — 그 문구를 건네면 직원이 그
  화면에서 그대로 보낼 수 있기 때문이고, 이 판정은 답변에 붙인 경고 문구가 아니라 코드가
  한다. 링크가 문구를 싣지 않게 된 뒤에도 이 게이트는 남는다 — 답변이 문구를 함께 주므로
  직원이 화면에 붙여넣을 수 있다는 사실은 그대로다.
  내부용 자료(`customer_facing`)는 여기서도 막지 않는다 — 주의로 알리고 직원이 판단한다(§7).
- **확인이 명확할 때만 연계한다.** 승낙이면 연계하고, 거절이면 취소하고, **어느 쪽인지
  분명하지 않으면 제안을 유지한 채 다시 묻는다** — 애매한 답을 승낙으로 해석하지 않는다.
  무엇을 연계하기로 한 것인지(어느 화면·어느 고객)는 제안한 턴이 남긴 것으로 정하고, 이번
  턴의 말에서 다시 추측하지 않는다.
- **제안은 그 자리에서만 유효하다.** 직원이 확인 대신 다른 질문을 하면 그 제안은 무효로 하고
  새 질문에 답한다. 걸어둔 제안을 몇 턴 뒤의 "네"로 실행하지 않는다.
- **연계 결과를 알린다.** 어느 화면을 열었는지 답변에 남기고, 조건이 맞지 않아 연계하지
  못했으면 왜인지 말한다.
- 새 화면을 붙일 때도 같다: 제안과 연계를 나누고, 링크에는 규격이 정의한 파라미터만 싣는다.

## 11. LLM 미연결이면 답하지 않는다

LLM 이 미설정이거나 죽어 있으면 **답변을 만들지 않고 "LLM 연결이 안 되어 있다"고
답한다.** 규칙·검색만으로 대신 답을 만드는 경로는 두지 않는다 — 근거가 덜 갖춰진 답변이 정상
답변처럼 보이는 것이 무응답보다 위험하다.

- 미연결 안내와 "지식베이스에 자료가 없다"를 같은 문장으로 말하지 않는다 — 뒤를 앞으로
  말하면 있는 자료를 없다고 답하는 셈이 된다. 원인(미설정·타임아웃 등)을 함께 남겨 진단이
  화면에서 끝나게 한다.
- 어느 단계에서 LLM 호출이 실패하든 결과는 같아야 한다 — 특정 단계만 예외를 처리하지 않아
  턴 전체가 오류로 끝나는 일이 없어야 한다.

## 12. 현재 구현과의 gap

기준과 구현의 알려진 차이. 여기 있는 항목은 **고쳐야 할 것**이지 기준의 예외가 아니다.
코드를 기준에 맞출 때 이 표에서 지워 나간다. (2026-08-26 코드 대조 기준)

번호는 **처음 적힌 것을 유지한다** — 커밋 메시지와 코드 주석이 그 번호로 이 표를 가리키기
때문에, 행이 지워졌다고 남은 행을 당겨 붙이면 지난 기록이 다른 항목을 가리키게 된다.

| # | 기준 | 현재 구현 | 방향 |
|---|---|---|---|
| 2 | §4 원문을 그대로 옮길 의무 없음 | **관계를 선언한 카드는 필수 인용 강제를 해제했다**(fact 24/64 — 아래 6번). 선언이 없는 카드는 `atomic` 스팬 + 필수 인용이 그대로다 | 저작이 넓어지는 만큼 카드 단위로 해제한다. 종류 단위로 한꺼번에 풀지 않는다 — 저작이 덜 된 카드의 오짝이 그날부터 통과한다.<br>**화면번호·조건문의 `atomic` 은 이 gap 이 아니다** — `[06-12-604]` 는 한 글자만 틀려도 없는 화면을 가리키는 **식별자**라 원문 그대로가 맞다. 이 gap 이 말하는 것은 값이 든 **문장**을 통째로 싣게 강제하는 것이다 |

2·6·7·12 는 모두 **지식 데이터가 관계·역할·시효성을 선언해야** 코드가 판정할 수 있는 것들이다

마쳤고(2026-08-25), 남은 것은 같은 순서를 다른 종류로 넓히는 일이다. 7 은 역할 축까지
선언으로 옮겼고(2026-08-26) 적용 조건 축이 남았다.

`channel`·`screen` 의 시효 표시는 그 구조를 미리 적용해본 예다(아래 16·18번) — 붙일지도

## 13. 아직 요건이 아닌 것 (예정)

여기 있는 것은 **지금 기준이 아니다.** 구현이 없어도 gap 이 아니다. 착수하기로 하면 해당
요건 절로 옮기고, 그때 §12 에 gap 행이 생긴다.

| 예정 | 무엇 | 착수 전에 정해야 할 것 |
|---|---|---|
| 대화 맥락 기반 답변 정정 | 상담 중 새로 알게 된 정보로 이전 답변을 갱신 제안한다 — "아까 국내주식 상품으로 안내드렸는데, 해외주식을 원하신다니 그쪽으로 다시 알려드릴까요?" | 답변 원문은 상담이력에 남고 이제 재료로 읽힌다(§3 상담 기록) — 막고 있던 것이 그거였다. 남은 것 둘: ① 프롬프트에 실리는 턴 기록은 여전히 질문·슬롯만 남기므로, 정정 판정을 **이번 턴 프롬프트**로 할지 **기록 조회**로 할지 정해야 한다 ② 기록은 발췌만 싣는다 — 정정하려면 어디까지 되살려야 하는지가 그 상한을 다시 정한다. 정정 제안도 §10 의 제안·확인 형태를 따른다(연계 대신 답변을 다시 주는 것) |
| 상담이력 기반 알림 | 이력을 관리해 필요한 시기에 직원에게 알린다 | 이력은 이미 턴마다 쌓인다. 없는 것은 "언제가 필요한 시기인가"의 판정 근거다 — 지식베이스 유래인지 운영 판단인지 정해야 한다(운영 판단이면 §8 대장에 등록). 알림을 어디로 띄울지(화면·별도 채널)도 정해야 한다 |
| 전략제안 표출물 질의응답 | 브리핑 화면에 뜬 것(제안 문장·전략 카드·근거·상품)에 대한 직원 질문에 답한다 | 재료 경로는 이미 있다(§3 고객 재료 — `customer` 도구가 화면에 뜬 AI 산문까지 싣는다). 정해야 할 것은 **어디까지가 「화면에 뜬 것」인가**다 — 전략 카드·근거·상품별로 화면이 실제로 노출하는 범위와 도구가 싣는 범위를 맞춰야 한다. 화면에 뜬 것과 다른 값을 말하지 않는다는 §3 규칙이 그대로 적용된다 |
| 시황·상품 재료 | 시장 상황과 운용 상품(추천펀드·디폴트옵션 포트폴리오·TDF 빈티지)을 근거로 답한다 | 재료는 이미 저작돼 있다 — `05_시황_상품_기반지식` 5개 문서가 `trigger_keywords`·`key_points`·`as_of` 프론트매터까지 갖췄는데 적재 경로가 없다(`../knowledge/CLAUDE.md` 적재 감사). 정해야 할 것 둘: ① 시황 수치는 주 단위로 낡아 §9 의 시효성 판정이 먼저 구현돼야 한다(§12 gap 12) ② `02_상품/01_퇴직연금펀드_포트폴리오` 는 `strategy_agent/data/portfolios.json`(루트 CLAUDE.md 가 "자리표시자"라 적어둔 것)의 실물이라, 대화형 카드로 적재할지 전략제안 카탈로그를 교체할지 먼저 정해야 §3 "같은 재료를 두 경로로 구현하지 않는다"를 지킨다 |
| 계산기 · 가능 여부 즉시 확인 | 07/01 ② 가 정의한 나머지 기능(같은 장의 반론 대응은 §3 화법 재료로, 판별 질문은 §5 로 요건화했고, 즉답 카드 양식은 §5 「양식은 요건이 아니다」로 내렸다) | 둘 다 재료 검색이 아니라 **계산·조회**라 도구 규약(§3)에 그대로 맞지 않는다. 가능 여부 확인은 고객 계좌 상태 조회라 연동 대상도 정해야 한다 |

## 14. 작업 규칙

**코드를 고쳤으면 §12 를 함께 본다.** 이 문서와 코드는 따로 흘러가면 둘 다 못 믿게 된다 —
기준서가 실제와 다르면 다음 사람이 기준서를 안 읽고, 안 읽으면 기준이 없는 것과 같다.
코드 수정마다 네 가지를 확인한다:

1. **지운 gap 이 있나** → §12 표에서 「지워진 gap」으로 내리고, 재발을 막는 회귀 테스트
   이름을 함께 적는다. 테스트 없이 내리지 않는다 — 다음 리팩터링이 조용히 되살린다.
2. **새로 어긋나게 된 것이 있나** → §12 에 **행을 추가한다.** 번호는 다음 번호를 쓴다.
   "나중에 정리하겠다"고 코드에만 두면 그 타협은 아무도 모르는 채로 굳는다.
3. **기준 자체를 바꿨나** → 해당 절의 본문을 고치고, 왜 바꿨는지를 그 자리에 남긴다
   (§5 「양식은 요건이 아니다」가 그 예다). 코드에 맞추려고 기준을 내리는 것과, 기준을
   다시 판단해 바꾸는 것은 다르다 — 뒤엣것만 허용된다.
4. **아직 하기로 정하지 않았나** → 요건으로 쓰지 말고 §13 에 둔다. §13 항목은 구현이
   없어도 gap 이 아니다.

새 재료·새 도구를 붙일 때 흔히 2번이 빠진다. 표시·경고를 코드 상수로 급히 붙이는 자리가
그렇다(§12 gap 16 이 그렇게 생겼다) — 데이터 선언으로 옮기지 못했으면 그 사실을 적는다.
- 지식 데이터의 구조·관계를 바꾸는 작업은 `../knowledge/CLAUDE.md` 를 기준으로 한다.
- 회귀 테스트(`tests/test_consult_agent.py`)는 현재 구현을 재고 있다 — gap 을 지우는
  코드 수정은 해당 테스트를 기준의 동작으로 함께 고친다(남은 것은 2·7번).

코드 수정 전후:

```bash
cd src
python -m tests.test_consult_agent           # 라우팅·도구 루프·가드 (LLM 키 불필요)
python -m pension_agent.consult_agent.kb     # 지식베이스 점검 리포트 — ERROR 0건 유지
```

지식베이스 원문·경로·공용 인프라를 함께 건드렸으면 루트 `CLAUDE.md` 의 전체 명령을 돈다.
