## 1. 요약

1. **우리 팀은 자산관리 AI 에이전트의 "판단 엔진"을 맡는다.** 판단 엔진은 고객 데이터에서 관리할 일을 찾고, 계산하고, LLM으로 고객별 제안을 만들고, 그 결과를 검증하는 부분이다. 고객 화면은 WM플랫폼 팀이 개발하고, DIC·디지털PB·M/L 플랫폼 등 기존 시스템은 각 부서 소유 그대로 엔진이 호출한다.
2. **WM 구현안(2026.10.6)은 "무엇을 할지"는 있지만 "LLM이 어떤 근거로 판단하고, 틀린 답을 어떻게 막는지"가 없다.** 이 기획안은 그 부분을 구체적으로 제시한다.
3. **1단계(비대화형)는 배치 구조다.** 매일 한 번 고객 데이터를 읽어 제안을 미리 만들고, 고객에게 나가기 전에 전부 자동 검증한 뒤, 앱 진입 시 카드와 push로 제공한다. **2단계(대화형)**에서 고객의 이벤트 입력, 금융제도·상품 질의를 받는다.
4. **LLM은 행내 기준이 없는 부분(예: 자산 비중 배분)도 판단한다.** 단, 직원이 규칙을 일일이 쓰지 않아도 관리할 수 있도록, 비교 기준선을 데이터에서 자동으로 만들고 LLM 판단이 기준선에서 벗어나거나 흔들리면 자동으로 안전한 기본값으로 바꾼다.
5. **개별 건을 사람이 처리하는 보류 대기열은 두지 않는다.** 모든 예외는 재생성 → 대체 → 미발송 순서로 자동 처리하고, 사람은 대체율·미발송율·실행률 세 비율과 신규 유형 배포 시 표본만 본다.
6. **퇴직연금 파일럿은 이 엔진의 작동 방식(근거 원장, 수치 검증, LLM 계획 루프, 미리 생성해 저장하는 브리핑)을 한 영역에서 검증한 사례다.** 1단계 엔진은 파일럿 부품을 재사용해 시작한다.

## 2. 배경 — WM 구현안에서 비어 있는 부분

- 목표: 고객이 묻기 전에 "지금 관리할 일"을 찾아 자문·실행·사후관리까지 연결하는 AI Agent
- 프로세스: Observe(살핀다) → Understand(이해한다) → Advise(제안한다) → Act(연결한다) → Follow-Up(관리한다)

## 5. 엔진 작동 방식

### 5.1 1단계 배치 흐름

매일 한 번(야간) 다음 순서로 실행한다.

| 순서 | 단계 | 담당 | 내용 |
|---|---|---|---|
| 1 | 데이터 수집 | 코드 | 고객별 보유 자산·부채·거래·만기·투자성향을 읽는다. 시황·기준 자료(하우스뷰, 금리, 비교집단 분포)는 해당 버전을 함께 기록한다 |
| 2 | 이슈 감지 | 코드 | 만기 도래, 큰 입출금, 금리 차이가 큰 부채, 자산 비중 쏠림, 절세 한도 미사용 등. 감지 조건은 행내 기준에서 가져온다 |
| 3 | 상황 구조화 | LLM | 감지된 이슈와 고객 데이터를 **고객 재무상황 양식**(§5.5)에 정리한다. 여러 이슈를 하나의 자금 계획 문제로 묶는다(예: 예금 만기 + 고금리 신용대출 + 전세대출 만기 → 하나의 자금 배분 문제) |
| 4 | 계산 | 코드 | 현금흐름 시뮬레이션, 이자 차이, 세액공제 금액, 상품 조건 필터. 수익률·물가 같은 가정값은 하우스뷰·행내 기준값으로 고정하고 LLM이 바꾸지 못한다 |
| 5 | 판단 | LLM | 대안 설계, 자산 비중 배분, 이슈 우선순위, 고객에게 보낼 1~2개 선택. 판단마다 이유를 기록한다 |
| 6 | 문장 작성 | LLM | 카드 문구와 push 문구 |
| 7 | 자동 검증 | 코드 | 수치·상품명 대조, 비교 표현 대조, 금지 표현, 기준선 이탈, 판단 흔들림, 기준 버전, 발송 빈도 (§5.4) |
| 8 | 자동 처리 | 코드 | 검증 실패 건은 재생성 → 대체 → 미발송 (§5.4) |
| 9 | 저장 | 코드 | 결과를 고객별 재무계획 저장소에 버전으로 저장. 각 제안이 기댄 입력값·기준 버전을 함께 저장 |
| 10 | 제공 | 화면(WM플랫폼) | 앱 진입 시 카드 표시, 우선순위 높은 건 push. **노출 직전**에 제안의 전제가 된 계좌 상태(잔액·보유 여부)가 바뀌었는지만 가볍게 확인(LLM 호출 없음). 바뀌었으면 노출하지 않고 다음 배치에서 다시 계산 |

배치를 택한 이유:
- 고객에게 나가기 전에 모든 결과를 검증할 수 있다. 실시간 생성에서는 불가능하다.
- 같은 날 생성된 결과를 고객 사이에서 비교할 수 있어서, LLM 판단의 일관성(§5.3)을 확인할 수 있다.
- 파일럿도 브리핑을 미리 생성해 저장하는 구조다(`strategy_agent/briefing_store.py`).

배치의 한계:
- 큰 지출 같은 이벤트는 다음 배치(보통 다음 날)에 반영된다. 자산관리 제안에서 하루 지연은 대부분 문제가 되지 않는다.
- 배치는 고객 데이터를 읽고, 생성 결과(고객의 금액·보유 상품 포함)를 저장한다. 결과 저장소도 고객 개인정보 저장소이므로, "배치로 하면 개인정보 저장 문제가 없다"고 볼 수는 없다. 실시간 방식과의 차이는 실시간 조회용 원천 데이터 복제본을 두지 않아도 된다는 점이다(§12 열린 항목).

### 5.2 LLM과 코드의 역할

| 하는 일 | 담당 | 이유 |
|---|---|---|
| 이슈 감지 조건 | 코드 | 행내 기준에서 가져온 조건이며, 같은 데이터에 같은 결과가 나와야 한다 |
| 금액·이자·세금·시뮬레이션 계산 | 코드 | 틀리면 안 되는 값이다 |
| 상품 후보 필터(가입 조건, 적합성) | 코드 | 상품 DB와 적합성 기준이 정한다 |
| 여러 이슈를 하나의 계획 문제로 묶기 | LLM | 이슈 조합은 미리 규칙으로 다 만들 수 없다. 기존 디지털PB 시나리오 방식의 한계가 이것이다 |
| 대안 설계와 자산 비중 배분 | LLM | 행내 기준이 없는 판단도 LLM이 한다. 관리는 §5.3의 자동 기준선으로 한다 |
| 이슈 우선순위(시급성·고객 영향·실행 가능성) | LLM | 계산 결과를 근거로 판단하고 이유를 기록한다 |
| 목표 사이의 선택(예: 은퇴자산 유지 vs 대출 활용) | **고객** (2단계) | 가치 판단이므로 엔진이 정하지 않는다. 엔진은 선택지별 계산 결과를 보여 주고, 고객이 고른 기준을 저장해 다음 계획에 적용한다. 1단계에서는 선택지를 받을 수단이 없으므로(§8) 시급성 순서만 적용한다 |
| 카드·push 문구 | LLM | |
| 결과 검증과 자동 처리 | 코드 | LLM이 검증을 우회하거나 끌 수 없어야 한다 |

원칙: **LLM은 판단과 문장을 맡고, 그 결과가 고객에게 나갈 수 있는지는 코드가 정한다.** 파일럿의 원칙("코드 = 근거의 경계와 계산 / LLM = 경계 안에서의 계획과 표현", 저장소 `CLAUDE.md` 절대 규칙 2)을 자산관리 전반으로 넓힌 것이다.

### 5.3 판단 등급과 자동 기준선

고객에게 나가는 모든 값과 제안에는 판단 등급이 붙는다. 화면에서 고객에게 보일지는 WM플랫폼 팀과 정하고, 내부 기록과 대시보드에는 항상 남긴다.

| 등급 | 조건 | 예시 |
|---|---|---|
| **기준** | 행내 기준을 코드가 그대로 적용한 값 | 세액공제 한도, 상품 가입 조건, 이자 차이 계산값 |
| **LLM 판단** | 행내 기준이 없어 LLM이 판단했고, 자동 점검(아래)을 통과한 값 | 투자자산 내 주식 비중 65%, 전세 만기 대비 예치 금액 4,000만 원 |
| **대체** | LLM 판단이 자동 점검에 걸려 안전한 기본값으로 바꾼 값 | 모델포트폴리오 비중, 계산값만 넣은 정형 문구, 전문가 상담 연결 |

**자동 기준선 — 직원이 범위를 미리 쓰지 않는다.** LLM 판단을 관리하는 기준선은 데이터에서 자동으로 만든다.

| 기준선 | 내용 | 갱신 |
|---|---|---|
| 비교집단 분포 | 연령·금융자산 규모·투자성향이 비슷한 행내 고객들의 실제 자산 비중 분포(하위 10% ~ 상위 10% 구간). WM 구현안 3.1.4에서 All Asset 포트폴리오의 상품 제안 방식으로 적은 "비교집단 참고 데이터"와 같은 개념이며, All Asset TF 산출물을 그대로 활용한다 | 배치마다 자동 재계산 |
| 모델포트폴리오 | DIC·하우스뷰의 위험등급별 모델포트폴리오 비중 | 소유 부서가 갱신하면 그대로 반영 |

**자동 점검 두 가지**

| 점검 | 방법 | 걸리면 |
|---|---|---|
| 기준선 이탈 | LLM이 정한 값이 비교집단 분포 구간과 모델포트폴리오 허용폭을 모두 벗어났는가 | LLM이 고객 데이터의 특정 항목(예: 17개월 뒤 전세대출 만기)을 이탈 사유로 지정했고 그 항목이 실재하면 통과. 아니면 모델포트폴리오 값으로 대체 |
| 판단 흔들림 | 같은 고객에 대해 LLM 판단을 3회 생성해 결과 차이가 허용폭(초기 제안값: 비중 15%p)을 넘는가 | 모델포트폴리오 값으로 대체 |

**이 방식이 기존 룰베이스와 다른 점**
- 룰베이스: 사람이 조건과 결과를 미리 다 쓴다. 쓰지 않은 상황은 처리하지 못한다.
- 이 엔진: LLM이 고객별로 판단하고, 관리는 데이터에서 자동으로 만든 기준선과의 비교로 한다. 사람은 규칙을 쓰지 않고, 대체가 많이 일어나는 이슈 유형만 본다.

**한계**: 비교집단 분포는 "다른 고객들이 실제로 어떻게 하고 있는가"이지 "무엇이 좋은가"가 아니다. 비슷한 고객 대부분이 예금에 몰려 있으면 기준선도 예금 쪽으로 치우친다. 그래서 전문가가 정한 모델포트폴리오를 함께 기준선으로 둔다.

### 5.4 자동 처리 원칙 — 보류 대기열을 두지 않는다

검증에 걸린 건을 사람이 하나씩 처리하면, 고객 수가 늘수록 관리 업무가 늘어난다. 그래서 개별 건은 전부 자동으로 처리한다.

| 처리 | 내용 |
|---|---|
| 재생성 | 같은 재료로 LLM에게 한 번 더 쓰게 한다 (1회) |
| 대체 | LLM 판단 대신 안전한 기본값을 쓴다: 모델포트폴리오 비중 / 계산값만 넣은 정형 문구 / 전문가 상담 연결 카드 |
| 미발송 | 이번 배치에서 보내지 않고 다음 배치에서 다시 계산한다 |

사유별 처리 방법은 `모니터링_설계.md` §2에 10개 사유 전부를 정리했다.

사람이 보는 것은 개별 건이 아니라 **비율 세 개**(대체율·미발송율·실행률)다. 사람이 개입하는 단위는 "고객 한 명"이 아니라 "이슈 유형 하나"이며, 대체율이 급증한 이슈 유형을 일시 중지하고 원인을 확인한다. 예외로, **새 이슈 유형을 처음 켜거나 프롬프트·모델을 바꿀 때만** 표본을 사람이 확인하고 켠다. 이것은 상시 업무가 아니라 배포 절차의 한 단계다.

이 방식의 비용: 대체가 일어난 고객은 개인화 수준이 낮은 결과(기본값, 정형 문구)를 받는다. 대체율이 곧 "LLM 개인화가 실패한 비율"이므로, 대체율을 낮추는 것이 엔진 품질 개선의 목표가 된다.

### 5.5 고객 재무상황 양식

LLM이 상황을 구조화할 때 채우는 양식이다. 화면·시뮬레이터·상품 필터·검증이 모두 이 양식을 공통으로 쓰므로, 엔진과 화면 사이 데이터 형식의 중심이 된다. **우리 팀이 정의한다.**

| 항목 | 예시 | 값마다 붙는 정보 |
|---|---|---|
| 자산 | 예금·적금·펀드·신탁·ISA·연금·외화·보험(해지환급금)·주택 | **구분**: 확정값(행내 데이터) / 고객 진술(2단계) / 추정값 · **기준 시점** · **출처** |
| 부채 | 신용대출·주택담보대출·전세자금대출 (금리, 만기, 월 원리금) | 같음 |
| 소득·지출 | 급여 입금액, 월 카드·자동이체 지출 | 같음 |
| 미래 자금 이벤트 | 전세 만기, 대출 만기, 상품 만기, 자녀 학자금, 은퇴 시점 | 같음 + 시점의 확실성 |
| 투자성향·투자기간 | 적극투자형, 5년 이상 | 같음 + 평가일 |
| 고객이 고른 기준 | "투자자산은 줄이지 않는다" (2단계) | 선택 일시 |

추정값에 기댄 제안은 (1) 추정값이 바뀌면 결과가 어떻게 바뀌는지를 함께 계산하고, (2) 되돌리기 쉬운 행동을 우선한다. 고객 진술 값에는 유효기간을 두고, 지나면 2단계 대화에서 다시 확인한다.

### 5.6 재무계획 저장소

| 저장 내용 | 쓰임 |
|---|---|
| 고객별 계획 버전 | 입력값이 바뀌지 않았으면 계획을 새로 만들지 않고 저장된 것을 보여 준다(같은 입력에 매번 다른 제안이 나가는 문제 방지) |
| 각 제안이 기댄 입력값과 기준 버전 | 입력값(예: 큰 출금)이나 기준(예: 하우스뷰)이 바뀌면 영향을 받는 제안만 골라 다시 계산한다 |
| 변경 사유 | 계획이 바뀌면 "무엇이 바뀌어서 계획이 바뀌었는지"를 카드에 표시한다 |
| 실행 여부 | 거래 데이터로 실행을 확인하고, 다음 계획은 실제 계좌 상태에서 계산한다 |

"고객을 기억하는 AI"(WM 구현안 중장기 목표)의 실제 내용이 이 저장소다. 파일럿은 대화 맥락을 프로세스 메모리에만 두고 있어(`docs/PRODUCTION_RISKS.md` §2-b) 이 부분은 새로 만든다.

### 5.7 2단계 — 대화형

1단계 배치 흐름에 다음이 더해진다.

| 단계 | 담당 | 내용 |
|---|---|---|
| 고객 입력 해석 | LLM | 고객이 말한 이벤트를 재무상황 양식에 반영할 값으로 바꾼다 |
| 해석값 확인 | 화면 | 계산 전에 "이렇게 이해했습니다: 전세 보증금 증액 3,000만 원(확정), 2028년 3월"을 보여 주고 고객이 확인한 값만 계산에 넣는다. LLM이 고객 말을 잘못 해석하면, 답변 수치가 전부 계산 결과 안에 있어도 계획 전체가 틀리기 때문이다 |
| 빈 칸 질문 | 코드가 대상 선정, LLM이 문장 | 시뮬레이터가 각 빈 칸의 값을 바꿔 보고 **결과를 크게 바꾸는 칸만** 질문 대상으로 고른다. WM 구현안의 "최소 질문 2~3개"를 고르는 구체적 방법이다 |
| 대안 반복 계산 | LLM 설계, 코드 계산 | LLM이 대안을 만들고 코드가 계산하는 과정을 반복한다. 반복 횟수 상한은 코드가 정한다(파일럿 `plan.MAX_STEPS`와 같은 방식) |
| 목표 선택 | 고객 | 선택지별 계산 결과를 보여 주고 고객이 고른다. 고른 기준은 저장되어 이후 배치에 적용된다 |
| 제도·상품 질의 | LLM + 근거 원장 | 파일럿 대화형 에이전트(`consult_agent`)의 방식: 도구로 근거를 모아 원장에 쌓고, 답변은 원장 안에서만 나오며, 원장 밖 수치는 검증에서 잘린다 |

## 6. 판단 기준의 출처

영역마다 행내에 이미 있는 기준을 출처로 지정하고, 파일럿과 같은 방법으로 엔진이 읽을 수 있게 변환한다.

| 영역 | 출처(예시) |
|---|---|
| 투자(펀드·ETF·신탁) | KB 하우스뷰 자산배분전략, DIC 모델포트폴리오 |
| 예적금·외화·여유자금 | 디지털PB 시나리오의 조건 규칙, 상품 DB, 고시 금리 |
| 보험 | 보험 포트폴리오 설계 기준(DIC 연계, 2026.10.8 예정) |
| ISA·연금(절세 수단) | 세법 기준, 행내 연금 지식베이스(파일럿) |
| 대출 | 여신 상품 기준, 금리 정보 |
| 세무·부동산 | 대면 전문가 상담(세무·부동산) 자료, 세법 기준 |
| 시황·뉴스 | 뉴스 검색 MCP, KB DAM, DART·CRETOP (PB 시황·RM 기업공시 에이전트와 연결) |
| 비교 기준선 | All Asset TF 비교집단 데이터, 행내 고객 보유 현황 |

- **위 표는 확정 목록이 아니라 예시다.** 0단계 첫 작업으로 영역별 행내 기준 자료를 전수 조사한다. 퇴직연금 파일럿에서 조사한 자료도 전체의 일부다.
- 변환 방법(파일럿에서 검증): 원문 → 기준표로 정규화(근거 등급 표시) → 엔진이 호출하는 도구 → 근거 원장 → 검증.
- 각 기준의 소유 부서는 그대로 인정한다. **우리 팀이 소유하는 것은 각 영역의 지식이 아니라, 행내 기준을 엔진의 판단 재료로 바꾸는 방법과 그 엔진이다.**

## 7. 알려진 허점과 보완 설계

설계 과정에서 찾은 허점과 보완 방법이다. "1단계" 열은 1단계 배치에서 적용하는지를 표시한다.

### 7.1 시간에 따른 변화

| # | 허점 | 실패 장면 | 보완 | 1단계 |
|---|---|---|---|---|
| A1 | 같은 입력에도 LLM 제안이 바뀐다 | 화요일과 목요일에 1순위 제안이 다름 | 계획을 버전으로 저장하고 입력이 바뀔 때만 다시 만듦. 판단 흔들림 자동 점검(3회 생성) | 적용 |
| A2 | 갑작스러운 지출 | 병원비 1,500만 원 출금 후에도 같은 제안 | 큰 입출금 감지 → 영향받는 제안만 재계산 → 변경 사유 표시 | 적용 (다음 배치) |
| A3 | 추정값이 나중에 정정됨 | 크게 추정한 금액으로 자금을 묶었는데 실제는 작음 | 값마다 확정/진술/추정 구분, 추정값 민감도 함께 계산, 되돌리기 쉬운 행동 우선 | 부분 (정정 입력은 2단계) |
| A4 | 고객이 말한 값이 오래됨 | 1년 전 급여로 계속 계산 | 진술 값 유효기간, 지나면 재확인 | 2단계 |
| A5 | 시장·기준이 바뀜 | 하우스뷰가 바뀌었는데 이전 기준 제안이 남음 | 제안마다 기준 버전 저장, 바뀌면 해당 제안만 미발송 후 재계산 | 적용 |
| A6 | 고객이 일부만 실행 | 3개 중 1개만 실행했는데 3개 다 한 것으로 계산 | 다음 계획은 실제 계좌 상태에서 계산 | 적용 |

### 7.2 입력과 계산의 정확성

| # | 허점 | 실패 장면 | 보완 | 1단계 |
|---|---|---|---|---|
| B1 | 검증은 "원장 안에 있는가"만 보고 "원장 값이 맞는가"는 보지 않는다 | 고객이 말한 "월 300"을 세전·세후 잘못 해석 → 모든 계산이 틀려도 검증 통과 | 고객 진술 해석값은 계산 전에 고객 확인 | 해당 없음 (1단계는 행내 데이터만 사용) |
| B2 | 어떤 빈 칸을 물을지 LLM이 정한다 | 결과를 뒤집는 값은 안 묻고 사소한 값을 물음 | 시뮬레이터 민감도로 코드가 질문 대상 선정 | 2단계 |
| B3 | 시뮬레이터 가정값(수익률·물가·금리)을 누가 정하나 | LLM이 대안마다 다른 수익률을 가정 | 가정값은 하우스뷰·행내 기준으로 코드가 고정 | 적용 |
| B4 | 영역 사이의 상호작용(세금·대출 한도)을 시뮬레이터가 모름 | 연금계좌 이전 자금의 중도인출 제약, DSR 한도를 빼고 계산 | 시뮬레이터에 세금·대출 한도 규칙 포함. 미반영 영역은 "계산에 반영하지 않음" 표시 | 적용 |
| B5 | LLM 결론이 계산 결과와 다를 수 있다 | 계산상 불리한 안을 "유리하다"고 씀 | 비교 순위는 코드가 계산, 비교 표현이 순위와 다르면 검증 실패 | 적용 |
| B6 | 타행 자산·부채를 모른다 | 타행 대출이 빠져 여유자금 과대평가 | 마이데이터 연동. 연동 전에는 "타행 부채 미반영" 표시, 결과를 크게 바꾸면 해당 이슈 미발송 | 적용 |

### 7.3 판단의 범위

| # | 허점 | 보완 | 1단계 |
|---|---|---|---|
| C1 | 목표 사이의 선택은 고객의 가치 판단이다 | 시급성 순서는 엔진, 목표 선택은 고객(2단계). 고른 기준 저장 | 시급성만 |
| C2 | LLM이 만든 대안 목록에서 좋은 대안이 빠질 수 있다 | 문제 유형별 표준 대안(행내 기준에서 가져옴)은 코드가 반드시 계산, LLM은 그 위에 조합 추가 | 적용 |
| C3 | 행내 기준·데이터가 없는 영역(재건축 사업성, 부동산 시세) | 추정하지 않음. 전문가 상담 연결 카드로 대체 (부록 사례) | 적용 |
| C4 | LLM 판단이 기준 없이 나간다 | 자동 기준선 + 이탈·흔들림 점검 + 대체 (§5.3) | 적용 |

### 7.4 운영

| # | 허점 | 보완 | 1단계 |
|---|---|---|---|
| D1 | 처음 보는 고객에게는 미래 자금 이벤트 정보가 없다 | 행내 데이터로 알 수 있는 이벤트(상품 만기, 대출 만기, 큰 입출금)부터 감지. 고객만 아는 이벤트는 2단계에서 받음 | 적용 |
| D2 | LLM 호출 비용과 처리 시간 | 야간 배치, 고객 1명당 생성 1~2건 + 판단 흔들림 점검 3회. 반복 상한은 코드가 정함 | 적용 |
| D3 | 제안이 좋은지 판정할 방법 | PB 검토 사례 모음(정답 세트)과 비교하는 회귀 시험, 실행률·실행 후 결과 추적 | 적용 |
| D4 | 배치 생성 후 고객이 거래해서 제안 전제가 바뀜 | 노출 직전 계좌 상태 확인, 바뀌면 노출 안 함 | 적용 |

## 8. 기존 디지털PB와의 차이

| 구분 | 기존 디지털PB | 1단계 엔진 |
|---|---|---|
| 제안을 만드는 방식 | 사람이 시나리오를 하나씩 만들고 관리 (약 90개) | 감지·계산은 코드, 이슈 묶음·비중 판단·문구는 LLM. 시나리오를 미리 쓰지 않음 |
| 여러 이슈가 겹친 고객 | 이슈별로 카드가 따로 나감 | 하나의 자금 계획으로 묶어 1~2개만 제안 |
| 행내 기준이 없는 판단 | 시나리오가 없으면 제안 없음 | LLM이 판단, 자동 기준선으로 관리 |
| 계획의 지속성 | 시점마다 독립된 카드 | 계획 버전 저장, 변화가 생기면 영향받는 제안만 재계산하고 변경 사유 표시 |
| 품질 관리 | 시나리오 단위 사전 검토 | 건별 자동 검증·자동 처리 + 이슈 유형별 비율 감시 |
| 대상 상품 | 은행권 WM상품 위주(예적금·외화·계열사 미추천) | 예적금·외화·대출·세무·부동산까지 한 계획 안에서 계산 |

**열린 항목 — 선택형 응답**: 카드 안에서 고객이 정해진 선택지(예: 전세 보증금 증액 예상 [없음] [3천만 원 이하] [3천~5천만 원] [5천만 원 이상] [모름])를 고르게 하면, 1단계에서도 고객만 아는 정보와 목표 선택을 받을 수 있어 디지털PB와의 차이가 더 커진다. 요구사항이 확정되지 않아 보류했다. 배치 구조에서도 **선택지별 결과를 배치에서 미리 생성하고 검증해 두는 방식**으로 추가할 수 있다(질문 1개, 선택지 4개 이하, 우선순위 1위 이슈에만 적용하면 생성량 증가는 감당 가능).

## 부록. 엔진이 어디서 전문가에게 넘기는가 — 재건축 사례

**고객 상황**: 1주택 보유, 재건축으로 몇 년 뒤 분담금 납부 예정, 이주 기간 전세 자금 필요, 월 급여·생활비·원리금 부담 있음, 은퇴까지 일정 기간 남음.

| 판단 | 엔진이 하는가 | 이유 |
|---|---|---|
| 현재 자산·부채·현금흐름 정리 | 한다 | 행내 데이터와 계산 |
| 이주 시점 전세 자금, 분담금 납부 시점의 부족액 계산 | 한다 (금액·시점이 주어지면) | 현금흐름 시뮬레이터 |
| 부족액을 메울 대안 비교(예금 만기 조정, 투자자산 일부 전환, 이주비·전세자금 대출) | 한다 | 상품 조건·대출 한도·이자 계산 |
| 분담금 금액·재건축 일정 추정 | **하지 않는다** | 행내 기준이 없다. 추정하면 그 추정값에 계획 전체가 기대게 된다 |
| 재건축 사업성, 입주권 관련 세금(대체주택 비과세 특례 등) 판단 | **하지 않는다 → 세무·부동산 전문가 상담 연결** | 개별 사실관계에 따라 결론이 달라지는 영역 |

1단계에서는 분담금·일정 정보를 받을 수단이 없으므로, 이 고객에게는 행내 데이터로 계산 가능한 부분(대출 금리 차이, 만기 자금 배분)만 제안하고, 재건축 관련 판단은 전문가 상담 연결 카드로 대체한다. 2단계에서는 고객이 분담금 통지 금액을 입력하면 확정값으로 계산한다.

엔진의 한계를 스스로 정의해 두면 "AI가 다 한다"는 주장보다 신뢰를 얻기 쉽다.
