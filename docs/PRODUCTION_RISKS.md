# 실서비스 전환 위험 — 지금 구조가 데모라서 성립하는 것들

> **손으로 쓰는 문서다.** 생성물인 `DEMO_STATUS.md`(무엇이 더미 **데이터**인가)와 역할이
> 다르다. 여기는 **무엇이 더미 구조인가** — 발표용 단일 프로세스라서 성립하고, 실서비스
> 프론트·백엔드를 붙이는 순간 깨지는 자리를 적는다.

이 저장소는 발표용 내부 데모다(루트 `CLAUDE.md`). 지금 도는 것은 `app.py`(Streamlit)
**한 프로세스**이고, 그 안에서 브리핑 화면과 대화형이 같은 메모리를 공유한다. 실서비스는
프론트를 따로 만들고 대화형 진입점은 FastAPI 핸들러를 상정한다(`graph.ask` 주석) — 그때
**«한 프로세스»라는 전제 위에 서 있던 것들이 조용히 깨진다.** 조용히 깨지는 것이 문제다:
아래 대부분은 예외를 던지지 않고 잘못된 값을 내거나 데이터를 잃는다.

각 항목은 **어디가 · 어떻게 깨지나 · 최소 조치**로 적는다. 심각도는 «틀린 답이 나가나»를
기준으로 매긴다 — 느린 것보다 틀린 것이 위다.

---

## 1. 상담이력 저장소가 동시 쓰기를 견디지 못한다 — 🔴 데이터 유실

**어디** `pension_agent/session_store.py::_save` · `append_turn`

파일 통째로 읽어 고치고 통째로 다시 쓴다. **잠금도, 원자적 교체(temp → `os.replace`)도
없다.** 그리고 `graph.ask()` 는 한 턴에 두 번 쓴다(직원 발화 · 에이전트 답변).

**어떻게 깨지나**

- 두 직원이 같은 고객을 동시에 상담하면(또는 워커가 여럿이면) 나중 쓰기가 먼저 쓰기를
  **덮는다** — 턴이 조용히 사라진다. 예외도 로그도 남지 않는다.
- 쓰는 도중 프로세스가 죽으면 JSON 이 잘린 채 남는다. 그러면 `_load` 의 `json.loads` 가
  예외를 던지고, **그 고객의 상담이력이 통째로 못 읽히게 된다** — `history` 도구도,
  브리핑 화면의 상담이력 섹션(REQUIREMENTS §14)도 함께 죽는다.

**왜 지금은 안 보이나** 단일 프로세스 · 단일 사용자 시연이라 동시 쓰기가 일어나지 않는다.

**최소 조치** 임시 파일에 쓰고 `os.replace` 로 교체(원자적) + 고객 단위 잠금.
**진짜 조치** 상담이력을 DB 로 옮긴다. 실서비스에서는 CRM 이 같은 자리를 채운다는 것이
이미 기준서의 전제다(consult_agent/CLAUDE.md 「상담 이력 — 소스가 둘이다」).

## 2. 브리핑 공유가 프로세스 안에서만 성립한다 — 🔴 화면과 다른 답

**어디** `pension_agent/strategy_agent/agent.py::propose` 의 `_BRIEFING_CACHE`

브리핑의 제안 문장·근거 해설은 LLM 이 쓰는 산문이라 **다시 만들면 다른 문장이 나온다.**
화면과 대화형이 같은 문장을 보게 하는 장치가 이 캐시인데, 캐시는 프로세스 안에만 있다.

**어떻게 깨지나** 워커가 여럿이면 브리핑 화면 요청과 대화 요청이 다른 프로세스에 떨어져
각자 생성한다 → 직원이 화면을 보며 물었는데 **화면에 없는 문장을 인용해** 답한다
(consult_agent/CLAUDE.md §3 «화면에 뜬 것과 다른 값을 말하지 않는다» 위반). 캐시
상한(`_BRIEFING_MAX`)에서 밀려나도 같은 일이 벌어진다.

**최소 조치** 브리핑 생성과 대화형을 한 프로세스에서 서비스한다(워커 1개 또는 세션 고정).
**진짜 조치** 생성된 브리핑을 저장소에 남겨 대화형이 읽는다. 정해야 할 것은
consult_agent/CLAUDE.md §13 「실서비스 프론트와 브리핑 공유」에 있다.

## 3. 원장이 갱신돼도 캐시를 비울 주체가 없다 — 🔴 낡은 값을 최신처럼 답함

**어디** `agent.clear_briefing_cache()` 를 부르는 운영 경로가 없다

실서비스의 고객 원장은 배치로 갱신된다. 지금 캐시 키는 프로파일 **내용**이라 프로파일이
바뀌면 키도 바뀌어 자연히 새로 만들어지지만, 그건 `get_profile` 이 **갱신된 프로파일을
돌려줄 때** 이야기다. 아래 4번처럼 프로파일 자체가 기동 시 메모리에 고정돼 있으면 캐시
이전에 원장이 낡는다.

**최소 조치** 배치 갱신 훅에서 `clear_briefing_cache()` 를 부른다.
**진짜 조치** 4번과 함께 푼다 — 프로파일을 요청마다 조회하면 이 문제는 사라진다.

## 4. 고객 데이터가 기동 시 메모리에 고정된다 — 🟡 교체 지점은 이미 있다

**어디** `pension_agent/strategy_agent/customer.py::get_profile` (`_BY_ID` 조회) ·
`AS_OF = date(2026, 8, 24)`

`get_profile` 은 **이미 교체 지점으로 설계돼 있다**(그 함수 주석이 그렇게 적고 있고,
대화형은 이 함수 하나만 의존한다). 남은 것은 두 가지다.

- 조회를 실제 저장소로 바꾸면 프로세스 기동 시 9명을 통째로 들고 있던 구조가 사라진다.
- **원장 기준일(`AS_OF`)이 상수다.** 실데이터에서는 배치 기준일을 읽어야 한다. 이 값은
  화면·답변의 «며칠 전 스냅샷»표기와 잔여일수 계산에 직접 들어간다(`date` 도구).

## 5. 진입점이 전부 동기 blocking 이다 — 🟡 동시 사용자 처리량

**어디** `graph.ask()` 와 그 아래 전부. `llm.agenerate()` 가 있는데 **아무도 쓰지 않는다.**

한 턴은 순차 LLM 호출 3~14 회다(고객 질문 3회 · 복합 지식 질문 5회 이상, 브리핑을 새로
만들어야 하면 14회). 그동안 호출 스레드는 묶여 있다.

**어떻게 깨지나** FastAPI 의 `async def` 핸들러에서 `ask()` 를 그대로 부르면 **이벤트
루프를 막아** 그 워커가 한 번에 한 요청만 처리한다. 직원 여럿이 동시에 쓰면 대기열이 된다.

**최소 조치** 핸들러를 `def`(동기)로 두거나 `run_in_threadpool` 로 감싼다 — 그러면
FastAPI 가 스레드풀에서 돌린다.
**진짜 조치** 파이프라인을 `agenerate` 기반 async 로 올린다(도구 병렬 실행도 그때 열린다).

## 6. LLM 클라이언트에 연결 재사용·재시도가 없다 — 🟡 지연과 실패율

**어디** `pension_agent/llm.py::_generate_genai`

- `urllib.request.urlopen` 을 호출마다 새로 쓴다 → **매 호출이 TCP+TLS 핸드셰이크부터**
  시작한다. 한 턴에 3~14 회면 그만큼 반복된다.
- **재시도·백오프가 없다.** 타임아웃은 60초 고정이고 레이트리밋(429) 처리도 없다.
  한 턴이 여러 호출이라 **턴 실패 확률은 호출 실패 확률의 누적**이다 — 한 번만 흔들려도
  그 턴은 "LLM 호출이 실패했습니다"로 끝난다(§11 규약대로 답을 지어내지는 않는다).

**최소 조치** 커넥션을 재사용하는 클라이언트로 바꾸고, 일시 오류(타임아웃·5xx·429)에
짧은 재시도를 둔다. 프로바이더 경계가 이 파일 하나라 호출부는 손대지 않아도 된다.

## 7. 턴마다 스레드를 만든다 — 🟢 부하가 커지면 본다

**어디** `pension_agent/consult_agent/nodes/answer.py`

되묻기 판정과 답변 작성을 동시에 돌리려고 턴마다 `ThreadPoolExecutor(max_workers=1)` 를
만든다. 동시 요청 수만큼 스레드가 생기고 상한이 없다. 시연 규모에서는 문제가 아니지만,
5번을 async 로 푸는 시점에 이 자리도 함께 정리하는 편이 낫다(그때는 스레드가 필요 없다).

## 8. 프로세스마다 지식베이스를 한 벌씩 든다 — 🟢 위험이 아니라 비용

**어디** `pension_agent/consult_agent/state.py::KB` (모듈 임포트 시 적재) ·
`graph._AGENT`(컴파일된 그래프)

실측 **0.23초 · 카드 569장 · 약 6MB**. 워커 수만큼 곱해지지만 이 규모에서는 문제가 아니다.
기동 시간과 메모리 산정에 넣어두라는 뜻으로만 적는다. 프로세스당 한 번이라는 성질 자체는
의도된 것이다(같은 카드를 여러 벌 들면 시효성 판정이 노드마다 갈린다 — `state.py` 주석).

## 9. 관측이 프롬프트를 외부로 내보낸다 — 🔴 실데이터 전환 시 개인정보 유출

**어디** `pension_agent/observability.py` · 켜는 스위치는 `.env` 의 `LANGFUSE_PUBLIC_KEY` ·
`LANGFUSE_SECRET_KEY`

LLM 호출마다 **프롬프트 전문과 응답 전문**이 Langfuse 로 나간다. 프롬프트에는 고객 원장이
그대로 실려 있다 — 이름 · 평가금액 · 보유상품 · 만기 · 투자성향, 그리고 대화형은 직원이
친 말과 지난 상담 기록까지.

**어떻게 깨지나** 지금은 고객이 시연용 목업 12명이라(루트 `CLAUDE.md`) 나가도 잃을 것이
없다. 실데이터로 바꾸는 순간, 기본값(`LANGFUSE_HOST` 미지정)은 **Langfuse Cloud** 라
고객 개인정보가 외부 SaaS 에 적재된다. 코드는 예외를 던지지 않고 조용히 잘 돈다 — 이
문서의 다른 항목과 같은 «조용히 깨지는» 부류다.

**왜 지금은 안 보이나** 키가 없으면 관측이 통째로 꺼져 있어서, 켜기 전까지는 아무 일도
일어나지 않는다.

**최소 조치** 셋 중 하나를 실데이터 전환 **전에** 정한다.
- 자체 호스팅 Langfuse 를 행내에 두고 `LANGFUSE_HOST` 를 그쪽으로 돌린다(망분리 환경에서
  외부 SaaS 는 어차피 닿지 않는다).
- `LANGFUSE_CAPTURE_CONTENT=0` — 본문 대신 길이만 나간다. 호출 횟수·지연·토큰·실패율은
  그대로 보이고, 프롬프트 내용만 사라진다.
- `LANGFUSE_ENABLED=0` — 통째로 끈다.

**진짜 조치** 무엇을 마스킹할지의 규칙을 정한다. 지금 스위치는 «전부 보내거나 전부
가리거나» 둘뿐이라, "고객명·계좌번호만 가리고 나머지는 본다"가 안 된다.

## 여기 적지 않는 것

- **무엇이 더미 데이터인가** — `DEMO_STATUS.md`(생성물)가 전담한다. 안내 콘텐츠, 금리
  자리표시자, 단말 딥링크 `mode=D`, 타겟 룰베이스 근거등급이 거기 있다.
- **기준과 구현의 차이** — `src/pension_agent/consult_agent/CLAUDE.md` §12(gap 표)가
  전담한다. 이 문서는 «기준을 지키고 있지만 단일 프로세스라서 지켜지는» 것을 적는다.
- **아직 하기로 정하지 않은 기능** — 같은 문서 §13.

## 고칠 때

위 항목을 실제로 고치면 **여기서 지우고**, 어디서 막는지(회귀 테스트·운영 설정)를 함께
적는다. 지우지 않으면 다음 사람이 이 문서를 안 믿게 되고, 안 믿는 문서는 없는 것과 같다
(consult_agent/CLAUDE.md §14 와 같은 규칙이다).
