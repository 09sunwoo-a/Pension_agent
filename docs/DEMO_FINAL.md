# 중간점검 시연 확정본 — 대화형 에이전트 (기획자 확정 3고객 + 이벤트 턴)

기획자가 `DEMO_CUSTOMER_SCENARIOS.md` 의 시나리오 라이브러리에서 세 고객을 추려 문구와
순서를 확정한 판이다(①~⑧). 여기에 **안내 콘텐츠 → 발송 화면 연계** 두 턴(E1·E2)을
김서연 뒤에, **상담 요약 → 쪽지 보내기** 두 턴(M1·M2)을 박정호 뒤에 더했다. 실행은 이
순서 그대로 리허설할 수 있다.

**①·③·⑦ 은 2026-09-03 에 바꿨다.** 브리핑 에이전트 확정본(`DEMO_GOLDEN_CASES_V2` 표시용)과
대조하니 ①③⑤⑥⑦⑧ 의 기대답변이 브리핑 화면(S2·S3·S4·기반지식)에 이미 문장으로 나와 있었다.
뒤 턴의 지시어(② 의 «옮기다», ④ 의 «그 돈»)와 능력 배분(⑥ 상담이력 · ⑧ 화면번호)을 지키면서
바꿀 수 있는 셋을 브리핑에 없는 지식으로 바꿨다 — 아래 표의 ①③⑦.

    cd src && python -m tests.debug.reps --final                 # 세 고객 전부
    cd src && python -m tests.debug.reps --final 이수민 --debug   # 고객 골라서 + 재료→답변 로그

> 이 문서는 손으로 쓴다(생성물이 아니다). 「기대답변」은 기대이지 보장이 아니다 — 문장은
> 매번 LLM 이 새로 쓴다. 전체 대본(`DEMO_SCENARIO.md`)의 발표자 멘트·«피할 질문»·리허설
> 체크는 여기에도 그대로 적용된다. 무엇이 더미인지는 `DEMO_STATUS.md` 가 갖고 있다.

## 시연에서 드러나야 하는 능력 넷

| | 능력 | 어느 턴이 보여주나 |
|---|---|---|
| ① | 실제 상담에 필요한 지식을 깊게 설명한다 (지식 베이스 기반) | ① ② ③ ⑧ |
| ② | 과거 맥락을 찾아낸다 (상담이력 관리) | ⑥ **M1** |
| ③ | 고객별 개인화된 솔루션을 정한다 (같은 질문도 고객별 다르게) | ④ ⑦ E1 |
| ④ | 현장 화법과 실제 업무까지 연결한다 (스크립트 · 업무 화면번호) | ④ ⑤ ⑧ **E2** **M2** |

E1·E2 는 ③과 ④를 함께 보여준다 — 이 고객 상태에 걸린 이벤트를 에이전트가 먼저 내밀고
(칩), 승낙하면 발송 화면을 열고 문구를 건넨다. 보낼지는 직원이 그 화면에서 정한다.
M1·M2 는 ②와 ④다 — 이번 상담에서 오간 대화를 에이전트가 읽어 요약하고, 승낙하면 직원
본인 쪽지함으로 보낸다. 쪽지는 고객이 아니라 직원에게 가는 행내 메모라 에이전트가 보내는
것까지 한다(연동 전 스텁 — 세션 기록에 남는다).

## 고객별 시연 역할

- **김서연 — 제도 적용.** 고객의 걱정(돈이 묶인다)에 중도인출 규정으로 답하고, 일부 전환
  가능 여부와 세액공제 효과까지 개인화해 설명한다. E1·E2 로 그 안내가 **고객에게 나가는
  문자**까지 이어진다.
- **이수민 — 상담 판단 및 화법.** 고객이 물은 디폴트옵션 수익률을 기준시점과 함께 답하고,
  현금성 대기자산·디폴트옵션 미등록에서 나오는 고객 반론에 바로 대응할 화법까지 준다.
- **박정호 — 상담기억에서 업무 실행까지.** 과거 상담을 찾아 현재와 연결하고, 재취업 예정
  고객의 계좌 분리 방법론과 과세이연 등록·입금·환급 절차·업무 화면을 안내한 뒤, 이번 상담을
  요약해 쪽지로 남긴다.

## 이벤트 턴을 김서연에 둔 이유

세 고객 중 김서연만 걸리는 콘텐츠가 **시연일과 무관하게 살아 있다.** 김서연에게 걸리는
것은 이벤트 2건(「IRP 추가입금하고 절세혜택 챙기기」 9/30까지 · 「ISA 만기자금, IRP로
이어가는 절세」 10/30까지)이고 8/24 고정 리허설과 실제 날짜에서 같다. 이수민의 세미나
(「디폴트옵션 점검」 9/10)와 박정호의 세미나(「연금개시 전 IRP 수령 방법」 9/8)는 하루짜리라
그 날이 지나면 후보에서 빠지고, 박정호의 것은 ⑦의 «환급 전 연금설계 등록 제한»과 나란히
놓기도 어색하다. 이수민에게 붙이고 싶으면 9/10 이전에만 성립한다.

## 리허설 체크 — 이 확정본에서 새로 볼 것

전체 대본의 리허설 체크(`DEMO_SCENARIO.md`)에 더해 아래를 본다.

- **② 가 되묻기로 끝나면 닫고 넘어간다.** 「일부만 옮겨도 돼?」는 세액공제를 직접 묻지
  않아 되묻지 않고 답할 수도 있고, 총급여 구간(원장에 없는 값)을 되물을 수도 있다.
  되물었으면 E1 로 가기 전에 **「초과야」로 한 턴 닫는다**(금액을 붙여 「5,500만원 초과야」라고 쓰면 계산기 도구가 그 5,500만원을 추가 납입액으로 읽는다 — `DEMO_CUSTOMER_SCENARIOS.md` 함정 ③) — 되묻기는 틀린 답을
  막는 장치인데(기준서 §5) 답 없이 다음 고객 질문으로 넘어가면 «답을 못 한 것»으로
  읽힌다. `reps --final` 은 이 턴을 넣지 않고 바로 E1 로 간다.
- **E1 답변이 이벤트 이름을 부르는가.** 발송 제안(`act._propose_lms`)은 답변이
  콘텐츠 이름을 인용했을 때만 붙는다. 등록 이름 끝의 «이벤트»·«세미나» 낱말과 공백은
  대조에서 무시한다(「IRP 추가입금하고 절세혜택 챙기기 (9/30까지)」도 인용이다 —
  2026-09-03 실측에서 그 표기가 탈락해 제안이 세미나로 갔었다). 후보만 늘어놓거나 이름을
  앞부분만 잘라 부르면 «열까요?»가 안 붙고 E2 가 「직전에 제안드린 작업이 없어요」로
  끝난다. 안 붙으면 질문을 「…뭐가 좋을까? 이름이랑 기간도 알려줘」로 고친다. E2 는
  `[75-08-110]` 딥링크와 «화면이 열리면 이 문구를 넣어 주세요»가 함께 나오면 된다.
- **E1 의 답에 세미나가 섞여도 발송은 이벤트로 간다.** 김서연에게 요건이 걸리는 세미나는
  없다(코드 판정 — 이벤트 2건뿐). 그런데 화면 ⑨ 는 세미나 칸을 비우지 않으므로 LLM 이
  열려 있는 세미나 5건 중 하나를 골라 넣고(LLM 이 없을 때만 임박 순 폴백), 그것이 대화
  재료로 함께 실린다 — 실측에서는 「원리금보장 67%」를 이유로 자산배분 세미나를 골랐다
  (편중 요건은 80% 이상이라 요건에 맞는 선정이 아니다). 답변이 그 세미나까지 말해도, 이벤트
  이름을 함께 불렀으면 제안은 이벤트에 먼저 붙는다(코드가 이벤트를 먼저 본다). 발표에서는
  세미나 쪽은 언급하지 않고 이벤트 발송으로 잇는다. 이야기에 더 맞는 ISA 이벤트(「ISA
  만기자금, IRP로 이어가는 절세」 10/30까지)는 선정 규칙(겹치는 요건 수 → 임박 순)에서
  추가입금 이벤트(요건 2건)에 밀려 뽑히지 않고, 도구는 뽑힌 1건의 문구만 실으므로 E2 로
  보낼 수 없다 — 질문을 받으면 그렇게 답한다.
- **① 은 중도인출 카드로 가야 한다.** 재료는 fact.k04.f29(법정 중도인출 사유 6가지)와
  fact.k04.f30(중도인출·해지 세율 16.5%)이다. 답이 ISA 전환 60일 규정으로 새면 브리핑
  화면과 같은 말이 된다 — 그때는 「중도인출 되는 사유가 뭐야?」로 좁혀 다시 묻는다. ① 뒤에
  ② 「일부만 옮겨도 돼?」가 오는 것은 그대로다(걱정 → 일부만).
- **③ 은 기준시점이 붙어야 한다.** 재료는 fact.k04.f62(디폴트옵션 수익률 순위 — 은행권 1위 ·
  42개사 중 2위, 25.4Q)이고 lineup(포트폴리오별 수익률)이 따라올 수 있다. 시점 없는 수익률은
  틀린 값과 구별되지 않으므로(기준서 §9) 답변에 «25년 4분기» 같은 시점이 없으면 생성이
  문제다. «보장»으로 읽히는 문장이 나오면 안 된다(§4 금지 표현).
- **이수민은 리허설 날짜에서 「만기 임박」 요건이 서지 않는다.** `reps` 는 오늘을 8/24 로
  고정해 D-33 이 되고, 만기 요건(`mat`)은 30일 창이다. 만기일·금액 자체는 재료에 실리므로
  ④⑤는 성립하지만 «관리 사유»에 만기가 빠진다. 이 고객만
  `PENSION_TODAY=2026-09-01 python -m tests.debug.reps --final 이수민` 으로 돌린다(골든
  케이스의 D-25). 실화면은 실제 날짜라 8/27 이후 그대로 성립한다.
- **⑦ 은 방법론 카드 m.096 이다** — 「퇴직 후 재취업 예정 고객 → 계좌를 3단(개시/퇴직용/
  적립용)으로 나눠 제안한다」. 답이 60일 재입금·환급으로 가면 브리핑 화면과 같은 말이고,
  그건 ⑧ 이 절차로 말한다. 예전 문구 「통장으로 받은 퇴직금, 지금이라도 IRP로 되돌릴 수
  있어?」(fact.k04.f47 · A 등급 실측)는 라이브러리 P2 에 남아 있다 — 브리핑과 겹쳐도 되는
  자리에서 쓴다.
- **⑧ 의 5단계는 절차 카드 proc.041 이 그대로 갖고 있다** — 「[06-12-501] 등록 → 60일 내
  입금 → 서류 발송 → 수정 요청 → 세금 환급」. 답변이 단계 수를 줄이거나 화면번호를 빼면
  재료가 아니라 생성이 문제다(`--debug` 로 어느 카드를 봤는지 확인). ⑧ 답변에는
  「06-12-501 화면 열기, 연계해드릴까요?」가 붙을 수 있다 — M1 로 넘어가면 그 제안은 자동으로
  무효가 된다(제안은 그 자리에서만 유효하다).
- **M1 은 `transcript` 도구로 가야 한다.** 이번 세션의 대화(⑥⑦⑧ 질문·답변)를 싣는 도구이고,
  `history`(지난 세션)와 갈린다. 도구 줄에 history 가 찍히고 «기록 없음»이나 지난 상담
  요약이 나오면 질문을 「지금까지 이 상담에서 얘기한 거 요약해서 쪽지로 보내줘」로 고친다.
  쪽지 제안(`act._propose_memo`)은 질문에 «쪽지»가 있고 transcript 를 썼을 때만 붙는다 —
  「요약해줘」만 하면 요약만 나오고 제안은 안 붙는다. 요약 본문은 검증을 거친 답변 그대로가
  쪽지가 되고, M2 는 그 본문을 다시 쓰지 않는다.
- **M2 는 «쪽지를 보냈어요 — 받는 사람: 본인»으로 끝난다.** 발송은 `send_memo` 스텁이라
  실제 메신저로 가지 않고 세션 기록(`session_data/`)에 남는다 — `reps` 는 실행 뒤 그
  디렉터리를 되돌린다. 받는 사람을 지정하는 문구(「팀장님께 보내줘」)는 아직 받지 않는다 —
  단말 연동 규격이 수신인을 정하면 그때 싣는다.
