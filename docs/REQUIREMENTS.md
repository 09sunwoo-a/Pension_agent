# 퇴직연금 AI 사후관리 에이전트 — 요건 앵커 문서

## 0. 이 문서의 지위와 갱신 규칙

**이 문서는 코드가 인용하는 유일한 규범 앵커다.** 코드 주석·docstring·`kinds.json` 설명·데이터
JSON 의 `note`·README 는 요건을 인용할 때 이 문서를 가리키고, 외부 기획안·목업 파일을 직접
인용하지 않는다.

그 이유는 이 문서가 생긴 계기 자체다 — 과거 `customer.py` 는 요건 판정의 기준을
`0. 기획/최종_퇴직연금_에이전트_v0.4.html` 로 못박고 있었는데, 그 경로는 저장소 어디에도
없었다. 상위 기획안은 계속 개정되므로, 특정 버전 파일명을 코드에 적으면 개정 즉시 코드의
근거가 검증 불가능해진다.

**상위 기준은 `06_에이전트_기능정의/`(팀원 설계)다.** 그 문서는 에이전트가 행원에게 무엇을·언제·
어떤 형태로 제공하는지를 영업 전·중·후·평상시 4시점으로 정의한 제품 기능정의이고, 이 문서는 그중
"① 영업 전 — 고객 1장 브리핑"을 ①~⑨ 화면 섹션의 구현 요건으로 번역한 것이다(대응표 §1.1). 두 문서가
충돌하면 06 문서를 기준으로 이 문서를 갱신한다 — 코드는 여전히 이 문서만 인용한다(06 문서의 ①~④는
시점 번호라 코드 식별자로 쓸 수 없다).

**갱신 절차** — 상위 소스(기획안·목업)의 변경이 요건에 영향을 주면:

1. 이 문서의 해당 절만 고친다. 코드 주석은 건드리지 않는다(아래 번호가 안정적인 한).
2. 부록 "변경 이력"에 한 줄 남긴다.
3. 코드가 그 규칙을 실제로 구현하는지 확인한다. 구현이 이미 다르다면 **이 문서가 현재
   구현을 반영하도록** 고친다 — "코드=사실" 원칙은 이 문서에도 적용된다. 문서가 코드보다
   앞서 나가면 이 문서 역시 검증 불가능한 인용처가 된다.

**번호 체계** — 아래 `§NN` 과 `①~⑨` 는 과거 기획 체계에서 그대로 승계한 식별자다. 연속
번호가 아니며(§1·§2·§4 등은 존재하지 않는다), 코드 ~48곳이 이미 이 번호로 서로를
가리키고 있어 재번호화하지 않는다. 새 규칙이 생기면 새 번호를 만들지 말고 관련 절 아래
소제목으로 추가한다.

## 2. ①~⑨ 화면 섹션 정의 · §15 섹션별 생성 주체

AI 브리핑 화면은 아래 9개 섹션으로 구성된다. `구현` 열은 `engine.section_summaries()` 가
쓰는 키이며, 코드의 단일 출처는 `src/strategy_agent/sections.py` 다(이 표와 1:1).

**§15 는 섹션마다 "무엇을 규칙이 정하고 무엇을 LLM 이 쓰는지"를 지정한다.** 이 분업이
"코드=사실" 원칙의 실체다 — 수치·상품명·선정 결과는 항상 코드가 정하고, LLM 은 그 재료를
문장으로 옮기거나 후보 중에서 고르기만 한다.

| # | 제목 | 구현 키 | 생성 주체(§15) |
|---|---|---|---|
| ① | AI 브리핑 | `ai_briefing` | Rule 재료 + LLM 문장화. 실패 시 문장을 **비운다**(규칙 문장으로 얼버무리지 않음). 매칭 전략이 없으면 규칙 상태 메시지 또는 Tier2 LLM 참고의견 |
| ② | 왜 이 고객님인가요 | `why_this_customer` | Rule(수치) + LLM(해석). 실패 시 규칙 문장 유지 |
| ③ | 현재 운용상태 | `current_state` | **LLM 전용** — 규칙 폴백 없음. 실패 시 비우고 "생성 안 됨" 표시(§6.1) |
| ④ | 수익률 상위 1% 고객님들이 많이 담은 상품은? | `top_holdings` | Rule(데이터) + LLM(해석 한 줄). 이 고객 대상 추천이 아니라 참고용(§7) |
| ⑤ | 이런 상품이 적합할 수 있어요 | `recommendation` | **LLM 전용** — 폐쇄 후보군 안에서만 선택. 실패 시 섹션을 비움(§9) |
| ⑥ | 이렇게 말해보세요 | `talking_points` | Rule 선정(정확히 2개 보장) + LLM 스크립트화 |
| ⑦ | 예상 반론 및 대응 화법 | `objections` | 반론 DB(Rule) + 선별(LLM) |
| ⑧ | 상담에 참고하세요 | `consult_resources` | 자료 DB(Rule) + 선별(LLM) |
| ⑨ | 고객님께 안내해보세요 | `outreach` | 콘텐츠 DB(Rule, 임박순) + 선별(LLM) + LMS 문구(LLM) |

화면은 ①~⑨ 를 모두 접어두고 섹션당 요약 2줄만 보여준 뒤 펼치게 한다
(`engine.section_summaries()`). 이 요약은 전부 코드 합성이라 LLM 검증(`verify()`)이 필요
없다 — 재료에 이미 있는 문장·이름·개수만 재배열하기 때문이다.

### LLM 미생성 표시

§15 가 LLM 몫으로 지정한 산출물이 빠지면, 규칙 문장으로 대신 채우지 않고 **빠졌다는 사실을
화면에 알린다**. `facts["llm_skipped"]` 에 사유가 남고 화면이 이를 표시한다. 이 키들은 섹션보다
잘게 나뉘어 있다(예: ⑨ 는 `outreach_event`·`outreach_seminar`·`lms_message` 셋으로 분리).
규칙으로 쓴 문장을 AI 산출로 오인시키지 않기 위한 장치다.

## 3. §3.1 · §3.2 — 고객 상단 표시 항목과 표기 통일

- **§3.1** 고객 화면 상단에는 연령·투자성향·평가금액·**최근 접촉**을 올리고, 스타클럽 등급은 값이
  있을 때만 연령 다음에 붙인다(06/01 ① 양식 "만 57세 · VIP", "최근 접촉: 없음 (6개월+)"). 최근 접촉은
  `Profile.dorm`(최종 접촉 이후 경과일)으로 "N일 전", 180일 이상이면 "없음(6개월+)"으로 표기한다.
  상단 항목의 유일한 출처는 `engine._customer_header()`(→ `facts["customer"]`)이고 한 줄 표기는
  `engine.customer_header_line()` 이다 — CLI·Streamlit 이 전부 여기서 읽는다.
  위험등급·거래채널은 적합성 게이트가 쓰는 엔진 내부 값이라 직원 화면에 노출하지 않는다.
- **§3.2** 적립금/잔액이 아니라 **'평가금액'** 으로 화면·프롬프트 표기를 통일한다.

생년월일·성별은 상단 후보였으나 `Profile` 에 아직 필드가 없다. 스타클럽 등급(`Profile.club_grade`)은
CRM 조인 값이라 없으면 생략한다.

## 4. §6.1 — ③ 현재 운용상태 코칭 2문장

③ 은 포트폴리오와 성과에 한정한 **국소적 진단** 2문장이다. ① AI 브리핑이 모든 요소를 종합한
최상위 전략인 것과 대비된다 — 두 영역의 역할을 분리해 중복을 방지한다(§17).

§15 가 이 섹션을 LLM 전용으로 지정했으므로 **규칙 폴백을 두지 않는다.** LLM 이 없거나
실패하면 비운 채로 "생성되지 않음"을 표시한다.

## 5. §7 — ④ 상위 1% 사례는 비교·참고 정보

④ 는 수익률 상위 1% 고객이 많이 담은 상품을 **비개인화** 사례로 보여주는 섹션이다. 이 고객
대상 추천이 아니며, 화면·CLI 모두 "이 고객 대상 추천 아님, 참고용" 문구를 함께 노출한다.
개인화 추천은 ⑤ 의 몫이고 적합성 게이트를 통과한 폐쇄 후보군에서만 나온다.

## 6. §8.2 — ⑤ 포트폴리오 예시 구성

⑤ 의 '포트폴리오 1개' 후보는 채권 40% + 채권 30% + 주식 30% 예시 구성을 기준으로 한다.
`strategy_agent/data/portfolios.json` 이 이 구성을 저장소의 실제 상품 카탈로그(P01~P12)로
재구성한 자리표시자 데이터이며, 데이터 담당자가 실제 추천 포트폴리오로 교체해야 한다.
구성 상품 **전부**가 적합성 게이트를 통과할 때만 후보로 노출한다.

## 7. §9 — ⑤ 상품추천 입력 3요소

상품 추천은 **고객상태 · 상품특성 · 시황** 3요소로 판단한다.

> **현재 구현 gap:** 시황(`src/market`)이 아직 연결되지 않아 **고객상태·상품특성 2요소로만**
> 판단한다. `src/market/README.md` 가 `current()` 읽기 계약만 확보해둔 미구현 플레이스홀더다.

고객상태 스냅샷에는 수익률·운용이력이 반드시 포함된다 — 빠지면 §17(추천 결과는 고객 상태
근거를 동반해야 한다)이 구조적으로 성립하지 않는다. 연금수령 개시 여부·투자기간도 입력이다.

### 연금수령 개시 계좌 — 추가납 권유 금지

`Profile.pension_started` 가 참이면 추가납 요건(`add`·`tax`)이 성립하지 않고(`customer.conditions()`),
브리핑 보유현황에 '납입여력' 대신 "연금수령 중 · 추가납입 불가"를 사실로 남긴다(`engine._briefing()`).
LLM 은 이 상태에서 추가납입을 권하지 않는다. 근거: 06/01 ① "⚠ 하지 말 것 — 연금개시 계좌 → 추가납
권유 금지", `05_주제별_추출지식/02_IRP관리방법론.md` 59 "연금개시(연금지급설계 등록) → 추가입금 불가".
(06/01 ① 의 "하지 말 것" 항목 중 규칙으로 옮긴 첫 건이다 — 나머지(금지 용어·민감 고객)는 §1.1 참고.)

## 8. §14 — 상담 이력

대화형 에이전트(`consult_agent`)가 **기록하고**, AI 브리핑(`strategy_agent`)이 **읽기만** 한다.
이 단방향 관계가 "코드=사실" 경계를 대화이력에도 그대로 적용한 것이다.

- 기록: `consult_agent/graph.py::ask()` 가 `customer_id` 를 받으면 매 턴(질문+답변)을
  `common/session_data/{customer_id}.json` 에 남긴다. 세션 단위는 `session_id` 다.
- 읽기: `common/session_store.py::summarize_for_briefing()` → `engine.prepare()` 의
  `facts["consult_history"]`. 어느 요약을 노출할지는 코드가 정한다(§15~§17 과 같은 원칙).

---

## 9. §17 — 근거 원칙

**추천 결과에는 고객 상태 근거가 존재해야 한다.** LLM 산출물은 `common/verify.py::verify()` 가
재료(facts) 밖의 수치·상품명을 쓰지 않았는지 재검증하고, 실패하면 결과를 채택하지 않는다.

섹션 간 역할도 분리한다 — ① 종합 전략과 ③ 국소 진단이 같은 말을 반복하지 않도록 각자의
관할을 나눈다(§6.1).
