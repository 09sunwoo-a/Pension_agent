# 퇴직연금 AI 사후관리 에이전트 — 요건 앵커 문서

## 0. 이 문서의 지위와 갱신 규칙

**이 문서는 코드가 인용하는 유일한 규범 앵커다.** 코드 주석·docstring·`kinds.json` 설명·데이터
JSON 의 `note`·README 는 요건을 인용할 때 이 문서를 가리키고, 외부 기획안·목업 파일을 직접
인용하지 않는다.

이 문서는 **전체 서비스 요건**이다. 대화형(consult_agent) 소관 요건·작업 규칙은
`src/pension_agent/consult_agent/CLAUDE.md` 한 곳에 있다 — §14·§18·§19 등 이 문서와
겹치는 규칙이 어긋나면 대화형 기준은 그 문서다.

그 이유는 이 문서가 생긴 계기 자체다 — 과거 `customer.py` 는 요건 판정의 기준을
`0. 기획/최종_퇴직연금_에이전트_v0.4.html` 로 못박고 있었는데, 그 경로는 저장소 어디에도
없었다. 상위 기획안은 계속 개정되므로, 특정 버전 파일명을 코드에 적으면 개정 즉시 코드의
근거가 검증 불가능해진다.

**상위 기준은 `07_에이전트_기능정의/`(팀원 설계)다.** 그 문서는 에이전트가 행원에게 무엇을·언제·
어떤 형태로 제공하는지를 영업 전·중·후·평상시 4시점으로 정의한 제품 기능정의이고, 이 문서는 그중
"① 영업 전 — 고객 1장 브리핑"을 ①~⑨ 화면 섹션의 구현 요건으로 번역한 것이다(대응표 §1.1). 두 문서가
충돌하면 07 문서를 기준으로 이 문서를 갱신한다 — 코드는 여전히 이 문서만 인용한다(07 문서의 ①~④는
시점 번호라 코드 식별자로 쓸 수 없다).

**갱신 절차** — 상위 소스(기획안·목업)의 변경이 요건에 영향을 주면:

1. 이 문서의 해당 절만 고친다. 코드 주석은 건드리지 않는다(아래 번호가 안정적인 한).
2. 부록 "변경 이력"에 한 줄 남긴다.
3. 코드가 그 규칙을 실제로 구현하는지 확인한다. 구현이 이미 다르다면 **이 문서가 현재
   구현을 반영하도록** 고친다 — "코드=사실" 원칙은 이 문서에도 적용된다. 문서가 코드보다
   앞서 나가면 이 문서 역시 검증 불가능한 인용처가 된다.

**번호 체계** — 아래 `§NN` 과 `①~⑨` 는 과거 기획 체계에서 그대로 승계한 식별자다. 연속
번호가 아니며(§1·§2·§4 등은 존재하지 않는다), 코드 ~48곳이 이미 이 번호로 서로를
가리키고 있어 재번호화하지 않는다. 새 규칙이 생기면 새 번호를 만들지 말고 관련 절 아래
소제목으로 추가한다.

## 2. ①~⑨ 화면 섹션 정의 · §15 섹션별 생성 주체

AI 브리핑 화면은 아래 9개 섹션으로 구성된다. `구현` 열은 `engine.section_summaries()` 가
쓰는 키이며, 코드의 단일 출처는 `src/strategy_agent/sections.py` 다(이 표와 1:1).

**§15 는 섹션마다 "무엇을 규칙이 정하고 무엇을 LLM 이 쓰는지"를 지정한다.** 이 분업이
"코드=사실" 원칙의 실체다 — 수치·상품명·선정 결과는 항상 코드가 정하고, LLM 은 그 재료를
문장으로 옮기거나 후보 중에서 고르기만 한다.

| # | 제목 | 구현 키 | 생성 주체(§15) |
|---|---|---|---|
| ① | AI 브리핑 | `ai_briefing` | Rule 재료 + LLM 문장화. 실패 시 문장을 **비운다**(규칙 문장으로 얼버무리지 않음). 매칭 전략이 없으면 규칙 상태 메시지 또는 Tier2 LLM 참고의견 |
| ② | 왜 이 고객님인가요 | `why_this_customer` | Rule(수치) + LLM(해석). 실패 시 규칙 문장 유지 |
| ③ | 현재 운용상태 | `current_state` | **LLM 전용** — 규칙 폴백 없음. 실패 시 비우고 "생성 안 됨" 표시(§6.1) |
| ④ | 수익률 상위 1% 고객님들이 많이 담은 상품은? | `top_holdings` | Rule(데이터) + LLM(해석 한 줄). 이 고객 대상 추천이 아니라 참고용(§7) |
| ⑤ | 이런 상품이 적합할 수 있어요 | `recommendation` | **LLM 전용** — 폐쇄 후보군 안에서만 선택. 실패 시 섹션을 비움(§9) |
| ⑥ | 이렇게 말해보세요 | `talking_points` | Rule 선정(정확히 2개 보장) + LLM 스크립트화. 후보는 문제상황 기반 |
| ⑦ | 예상 반론 및 대응 화법 | `objections` | 반론 DB(Rule) + 선별(LLM). 후보는 문제상황 기반 |
| ⑧ | 상담에 참고하세요 | `consult_resources` | 자료 DB(Rule) + 선별(LLM). 관리 방법론 + 노하우 화법 + 업무처리 절차(화면번호)를 번갈아 |
| ⑨ | 고객님께 안내해보세요 | `outreach` | 콘텐츠 DB(Rule, 문제상황 관련도→임박순) + 선별(LLM) + LMS 문구(LLM). 이벤트·세미나는 현재 **더미**(아래 표시 규약) |

화면은 ①~⑨ 를 모두 접어두고 섹션당 요약 2줄만 보여준 뒤 펼치게 한다
(`engine.section_summaries()`). 이 요약은 전부 코드 합성이라 LLM 검증(`verify()`)이 필요
없다 — 재료에 이미 있는 문장·이름·개수만 재배열하기 때문이다.

### 문제상황 정의 — ⑥⑦⑧⑨ 의 출발점

⑥~⑨ 는 전략(①~⑤)이 아니라 **이 고객이 왜 관리 대상인가**에서 출발한다. 근거는
`06_주제별_추출지식/01_고객세그먼트.md` 이며, 각 세그먼트는 `segment` kind 레코드로 등록돼
"어떤 요건 조합이면 성립하는가(`conds`)" 와 "어떤 상태면 제외인가(`exclusions`)" 만 데이터로
선언한다. 판정 규칙과 임계값은 `customer.conditions()` 코드 그대로다 — 세그먼트가 새 판정
로직을 만들지 않는다. 원문 임계값이 코드와 다른 항목은 레코드 `note` 에 차이를 남기고 코드를
바꾸지 않는다(임계값 통일은 팀 합의 사항).

매칭은 `strategy_agent/situations.py::problem_situations()` 가 하고, 결과는
`facts["problem_situations"]` 로 화면 ⑥ 위에 한 줄 노출된다. 성립 요건이 하나도 없는 고객은
문제상황도 0건이며, ⑥⑦⑧ 도 비운다 — 관리 사유가 없는 고객에게 사유를 만들어내지 않는다.

세그먼트에서 화법·자료로 가는 연결은 3단이다: ① 카드에 세그먼트가 직접 걸려 있으면 그것 →
② 세그먼트 그룹 ↔ 화법·절차 그룹 매핑 → ③ 세그먼트 이름·조건문과의 n-gram 유사도.
①은 사람이 확정해야 하는 저작이라 아직 비어 있고, 지금은 ②+③ 이 후보를 만든다.

**이 후보군은 대화형도 함께 쓴다.** 화면 ⑥⑦⑧ 은 상담 **전에** 후보군에서 정확히 2건씩
골라 고정하고 나머지를 자르는데, 대화형은 상담 **중에** «방금 나온 상황»까지 보고 그 나머지
중에서 고른다(`consult_agent/CLAUDE.md` §3 「고객 상태에 걸린 화법」). 후보군을 공유하는
것이 상충 방지 장치다 — 대화형이 자기 매칭을 만들면 같은 질문에 화면과 다른 카드를 말하게
되고, 세그먼트 `exclusions` 로 막아둔 것(연금개시 계좌의 납입 권유)도 그쪽에서 되살아난다.
매칭 함수는 `support/matching.py` 하나이며, 관련도가 필요한 소비부는
`scored_situation_cards()` 를 쓴다.

### 지식베이스 출처 보존 — 01~04 역추적

06 추출지식은 01~04 원본에서 다시 뽑은 것이라 출처·게시시점이 약식이다. 그래서 원본 문서를
`doc` kind 레지스트리로 따로 등록하고(문서명·부서·게시시점·신뢰 등급), 모든 카드가
`source.doc` 로 그것을 가리킨다. 화면과 대화형 답변은 이 레지스트리를 조인해 **원천 문서명과
기준시점**을 함께 보여준다 — 적재 파일명이 아니라 행원이 아는 문서 이름으로 말해야 근거가 된다.

출처를 특정하지 못한 인용은 값을 지어내지 않고 원문 표기를 `source_text` 로 남긴다.
작성자 실명·부점·직급은 옮기지 않는다(`src/AUTHORING.md` §4) — 글번호와 게시일이 레지스트리에
있어 추적에는 그것으로 충분하다.

### ⑨ 콘텐츠 더미 표시 규약

실제 콘텐츠 캘린더 연동이 확정되기 전까지 ⑨ 의 이벤트·세미나는 더미 데이터다. 저장소에 있는
실제 마케팅 콘텐츠는 전부 데모 기준일(`customer.TODAY`) 이전에 종료된 것이라, "종료된 콘텐츠는
노출하지 않는다"는 요건을 지키면서 화면을 검증하려면 날짜를 지어내야 하기 때문이다.

더미는 세 표시를 **함께** 단다 — `dummy: true`(기계 판독) · 이름 앞 `(더미) `(화면) ·
LMS 문구 앞 `[더미] `(발송문). 셋 중 하나만 있으면 `strategy_agent/test_support.py` 가
실패시킨다. LLM 이 문구를 다시 쓸 때도 `[더미] ` 접두는 코드가 다시 붙인다. 실제 콘텐츠로
교체할 때는 세 표시를 함께 지우고 출처를 넣는다.

### LLM 미생성 표시

§15 가 LLM 몫으로 지정한 산출물이 빠지면, 규칙 문장으로 대신 채우지 않고 **빠졌다는 사실을
화면에 알린다**. `facts["llm_skipped"]` 에 사유가 남고 화면이 이를 표시한다. 이 키들은 섹션보다
잘게 나뉘어 있다(예: ⑨ 는 `outreach_event`·`outreach_seminar`·`lms_message` 셋으로 분리).
규칙으로 쓴 문장을 AI 산출로 오인시키지 않기 위한 장치다.

## 3. §3.1 · §3.2 — 고객 상단 표시 항목과 표기 통일

- **§3.1** 고객 화면 상단에는 연령·투자성향·평가금액·**최근 접촉**을 올리고, 스타클럽 등급은 값이
  있을 때만 연령 다음에 붙인다(07/01 ① 양식 "만 57세 · VIP", "최근 접촉: 없음 (6개월+)"). 최근 접촉은
  `Profile.dorm`(최종 접촉 이후 경과일)으로 "N일 전", 180일 이상이면 "없음(6개월+)"으로 표기한다.
  상단 항목의 유일한 출처는 `engine._customer_header()`(→ `facts["customer"]`)이고 한 줄 표기는
  `engine.customer_header_line()` 이다 — CLI·Streamlit 이 전부 여기서 읽는다.
  위험등급·거래채널은 적합성 게이트가 쓰는 엔진 내부 값이라 직원 화면에 노출하지 않는다.
- **§3.2** 적립금/잔액이 아니라 **'평가금액'** 으로 화면·프롬프트 표기를 통일한다.

생년월일·성별은 상단 후보였으나 `Profile` 에 아직 필드가 없다. 스타클럽 등급(`Profile.club_grade`)은
CRM 조인 값이라 없으면 생략한다.

## 4. §6.1 — ③ 현재 운용상태 코칭 2문장

③ 은 포트폴리오와 성과에 한정한 **국소적 진단** 2문장이다. ① AI 브리핑이 모든 요소를 종합한
최상위 전략인 것과 대비된다 — 두 영역의 역할을 분리해 중복을 방지한다(§17).

§15 가 이 섹션을 LLM 전용으로 지정했으므로 **규칙 폴백을 두지 않는다.** LLM 이 없거나
실패하면 비운 채로 "생성되지 않음"을 표시한다.

## 5. §7 — ④ 상위 1% 사례는 비교·참고 정보

④ 는 수익률 상위 1% 고객이 많이 담은 상품을 **비개인화** 사례로 보여주는 섹션이다. 이 고객
대상 추천이 아니며, 화면·CLI 모두 "이 고객 대상 추천 아님, 참고용" 문구를 함께 노출한다.
개인화 추천은 ⑤ 의 몫이고 적합성 게이트를 통과한 폐쇄 후보군에서만 나온다.

## 6. §8.2 — ⑤ 포트폴리오 예시 구성

⑤ 의 '포트폴리오 1개' 후보는 채권 40% + 채권 30% + 주식 30% 예시 구성을 기준으로 한다.
`strategy_agent/data/portfolios.json` 이 이 구성을 저장소의 실제 상품 카탈로그(P01~P12)로
재구성한 자리표시자 데이터이며, 데이터 담당자가 실제 추천 포트폴리오로 교체해야 한다.
구성 상품 **전부**가 적합성 게이트를 통과할 때만 후보로 노출한다.

## 7. §9 — ⑤ 상품추천 입력 3요소

상품 추천은 **고객상태 · 상품특성 · 시황** 3요소로 판단한다.

> **현재 구현 gap:** 시황(`src/market`)은 `current()` 가 **데모 금리표**(`rates_demo.json`,
> `dummy: true`)를 돌려주는 자리표시자 구현이다. 화법 카드의 금리 슬롯과 주장 성립 조건이
> 이 값을 쓰지만(§18), ⑤ 상품 추천은 아직 **고객상태·상품특성 2요소로만** 판단한다.
> 실제 피드가 붙으면 `market/__init__.py` 본문만 교체한다.

고객상태 스냅샷에는 수익률·운용이력이 반드시 포함된다 — 빠지면 §17(추천 결과는 고객 상태
근거를 동반해야 한다)이 구조적으로 성립하지 않는다. 연금수령 개시 여부·투자기간도 입력이다.

### 연금수령 개시 계좌 — 추가납 권유 금지

`Profile.pension_started` 가 참이면 추가납 요건(`add`·`tax`)이 성립하지 않고(`customer.conditions()`),
브리핑 보유현황에 '납입여력' 대신 "연금수령 중 · 추가납입 불가"를 사실로 남긴다(`engine._briefing()`).
LLM 은 이 상태에서 추가납입을 권하지 않는다. 근거: 07/01 ① "⚠ 하지 말 것 — 연금개시 계좌 → 추가납
권유 금지", `06_주제별_추출지식/02_IRP관리방법론.md` 59 "연금개시(연금지급설계 등록) → 추가입금 불가".
(07/01 ① 의 "하지 말 것" 항목 중 규칙으로 옮긴 첫 건이다 — 나머지(금지 용어·민감 고객)는 §1.1 참고.)

## 8. §14 — 상담 이력

대화형 에이전트(`consult_agent`)가 **기록하고**, AI 브리핑(`strategy_agent`)이 **읽기만** 한다.
이 단방향 관계가 "코드=사실" 경계를 대화이력에도 그대로 적용한 것이다.

- 기록: `consult_agent/graph.py::ask()` 가 `customer_id` 를 받으면 매 턴(질문+답변)을
  `src/session_data/{customer_id}.json` 에 남긴다. 세션 단위는 `session_id` 다.
- 읽기: `pension_agent/session_store.py::summarize_for_briefing()` → `engine.prepare()` 의
  `facts["consult_history"]`. 어느 요약을 노출할지는 코드가 정한다(§15~§17 과 같은 원칙).

---

## 9. §17 — 근거 원칙

**추천 결과에는 고객 상태 근거가 존재해야 한다.** LLM 산출물은 `pension_agent/verify.py::verify()` 가
재료(facts) 밖의 수치·상품명을 쓰지 않았는지 재검증하고, 실패하면 결과를 채택하지 않는다.

섹션 간 역할도 분리한다 — ① 종합 전략과 ③ 국소 진단이 같은 말을 반복하지 않도록 각자의
관할을 나눈다(§6.1).

## 10. §19 — 상담결과 반영 (예약)

`pension_agent/session_store.py` 의 턴 레코드에 `outcome` 필드를 예약해두었다. 상담 결과를 다음
브리핑 생성에 반영하는 루프는 아직 구현하지 않았다 — 그 루프가 "코드=사실" 경계를 어떻게
지킬지 별도 설계가 필요하다.

## 11. §18 — 데모 규약과 시효성 수치

이 저장소는 **발표용 내부 데모**다. 실데이터 전환 전이고, 그 사실이 요건 몇 개의 모양을 바꾼다.

### 화면과 대화형의 분담

브리핑은 고객 화면 **왼쪽**, 대화형은 **오른쪽**이다. 07/01 ① 7요소 중 3(고객이 모르는 자기
현황)과 6(하지 말 것)은 화면 섹션을 만들지 않고 대화형이 맡는다 — 둘 다 "지금 이 고객을 어떻게
대할 것인가"라 상담 흐름 안에서만 의미가 있다.

- **자기 현황**: `facts["briefing"]` 에 `당해_납입액`·`예상_세액공제액` 을 싣는다. 재료에 없으면
  `briefing_qa` 가 답을 써도 `verify()` 가 재료 이탈로 거부한다 — 값은 `Profile` 에 있는데
  답을 못 하던 상태가 정확히 그것이었다.
- **하지 말 것**: `consult_agent/guard.py`. **지식베이스에 있는 것만** 쓴다 —
  `method.cautions` 중 역할이 caution 으로 선언된 것과 민감 응대 화법 카드.
  `procedure.cautions` 는 형태만 같고 본체가 문서 검증 메모("필자 해석 / 확인 필요")라
  변환기가 일괄 authoring 으로 선언해 제외된다(역할 선언: `knowledge/CLAUDE.md` §3). 재료가 없는 요건에는 아무것도
  띄우지 않는다. 경고는 코드가 붙이고 톤은 프롬프트가 잡는다 — `verify()` 가 톤을 검사하지
  않으므로 둘 다 필요하다.

### 더미 표시 규약 (⑨ 규약 대체)

발표 산출물에 딱지를 남기지 않는다. 표시는 **기계판독 `dummy: true` 하나뿐**이고, 화면 이름의
`(더미) ` 와 발송문의 `[더미] ` 접두는 쓰지 않는다.

접두를 떼면 스텁이 실제 연동으로 바뀔 때 지어낸 일정이 고객 문자로 나가므로, 보호막을 텍스트에서
**게이트**로 옮겼다 — `pension_agent/tools.py::send_lms()` 가 `dummy` 자산의 발송을 거부한다.
접두는 LLM 이 문구를 다시 쓰면서 지울 수 있지만 게이트는 못 지운다.

### 화법 카드의 시효성 수치

원문(`quotes`·`source_text`)은 어떤 경우에도 고치지 않는다. 대사는 **골격 + 슬롯**으로 다룬다.

| 구분 | 대상 | 처리 |
|---|---|---|
| 금리 슬롯 | 5건 (`config.RATE_SLOTS`) | 파생 텍스트의 금리 표기를 `market.current()` 현재값으로 치환. 대사에 없고 인용문에만 있으면 "원문 X · 현재 Y" 참고 표시 |
| 주장 성립 조건 | 5건 (`config.CLAIM_CONDITIONS`) | `compare` 는 조건이 깨지면 후보군에서 **격리**, `unknown` 은 판정 근거가 없어 **확인 요구** 경고 |
| 제도 상수·가정치 | 나머지 | 무변경 — "현재 값"이 없는 값들이다 |

"은행권 1위"·"~보다 높다"는 수치에 딸린 수식어가 아니라 대사의 결론이라, 수치만 최신화하면
결론이 조용히 거짓말이 된다. 그래서 조건을 선언하고 판정은 코드가 한다 — 세그먼트가
`conds`/`exclusions` 만 선언하는 것과 같은 구조다.

격리는 `kb.load_kb()` 한 곳에서 한다. `kb.pitches` 를 보는 소비처가 넷(검색·⑥⑦ 후보군·반론
DB·카드 인덱스)이라 각자 거르게 두면 언젠가 한 곳이 빠진다.

### 소스 미확정 필드

데이터딕셔너리에서 대응 컬럼을 찾지 못한 `Profile` 필드가 6개다 — `matDD`/`matAmt`(만기) ·
`room`(잔여 한도) · `income_bracket`(총급여) · `dorm`(최근 접촉) · `retPct`(수익률 백분위) ·
`pension_started`(연금개시 여부). 데모에서는 전부 더미로 채워 화면을 매끄럽게 보이게 한다.

단 `retPct`·`dorm` 은 `None` 으로 올 수 있게 방어한다 — 피어그룹 산출과 CRM 조인이라 실데이터
전환 초기에 가장 늦게 붙을 값이고, 이전 구현은 `None` 을 정수와 비교해 브리핑 전체를
TypeError 로 죽였다. 값이 없으면 해당 요건만 성립하지 않는다(`matDD` 가 이미 쓰던 방식).

### 무엇이 더미인지 아는 방법

화면에 표시가 없으므로 `docs/DEMO_STATUS.md` 가 전담한다. **생성물이다** —
`python -m scripts.demo_status` 가 코드에서 뽑아 덮어쓴다. 손으로 적으면 반드시 코드와
어긋나고, 어긋난 순간부터 아무도 믿지 않는다.
